## 1. 文書の役割

本書は、本システムのローカル開発環境構築、外部サービス設定、DB migration、Vercel へのデプロイに必要な手順をまとめる。

システム構成自体は [設計書](./設計書.md)、テスト分類は [テスト方針](./テスト方針.md)、稼働後の監視・障害対応は [運用保守手順書](./運用保守手順書.md) を参照する。

## 2. 前提環境

必要な主なツール・サービス:

- Git
- Node.js
- pnpm
- Docker 等のコンテナランタイム（Medium Test 用）
- AWS CLI（Production DB backup の手動確認・restore 用）
- Vercel
- Neon PostgreSQL
- Cloudflare R2
- LINE Developers / LINE Login / LIFF
- 必要に応じて Sentry

ローカル開発で使用する Node.js の exact version は `mise.toml` を Source of Truth とする。pnpm は従来どおりルート `package.json` の `packageManager` を Source of Truth とする。Vercel の Node.js は `package.json` の `engines.node` で 24.x を指定し、minor / patch version は Vercel 側で更新される。

本システムのバージョンはルート `package.json` の `version` を Source of Truth とする。`apps/*` と `packages/*` の内部 workspace は、独立した公開・独立したリリースを行わない限り個別 version を持たない。将来、独立公開・独立リリースする workspace が生じた場合は、その workspace に限って個別 SemVer を導入できる。リリースブランチで、ルート `package.json` の `version` をリリース対象の SemVer へ更新する。

主要なデプロイ単位は `apps/web` の単一 Next.js アプリである。staff、`/admin`、Server Components、Server Actions を同じ runtime で提供する。

## 3. ローカル環境構築

```sh
git clone <REPOSITORY_URL>
cd TimeCard
pnpm install --frozen-lockfile
```

通常の Web 開発サーバー:

```sh
pnpm dev:web
```

実 LINE / LIFF 認証を利用するローカル開発では `pnpm dev:web:local` を使用する。詳細は「staff で実 LINE 認証を使うローカル開発」を参照する。

必要な環境変数名と設定有無は、`apps/web/.env.example`、root `.env.local.example`、各 server package の env 定義を Source of Truth とする。ローカルでは必要な値を `.env` 系ファイルへ設定し、実値や secret はコミットしない。

各 workspace は、環境変数を実際に利用するフェーズで必要な値と形式を検証する。`NEXT_PUBLIC_*` のように build artifact へ埋め込まれる公開設定や、Sentry の source map upload のように build 処理自体が参照する設定は build-time configuration として build 時に利用・検証する。一方、`DATABASE_URL` や `LINE_CHANNEL_ID` のように build artifact へ埋め込まない server runtime 設定は Web build の必須入力にせず、実際にその設定を必要とする runtime 処理または明示的な runtime configuration validation で不足・形式不正を検出する。

build-time configuration と runtime configuration は一律に扱わない。runtime で必須の設定を optional 扱いにはせず、必要な runtime 境界で明確に失敗させる。

標準品質確認:

```sh
pnpm quality
```

テスト分類と個別コマンドは [テスト方針](./テスト方針.md) を参照する。

## 4. PostgreSQL / Neon

Local、develop / Preview、Production は接続先を分離する。共有 Preview DB や Production DB をローカルテストの検証先として使用しない。

DB 接続に必要な環境変数は `packages/db/.env.example` と DB 実装を Source of Truth とする。接続文字列の実値は secret 管理へ保存し、文書やソースへ記載しない。

Preview / Production で migration または Attendance Current State Projection rebuild を行う maintenance operation は、通常 runtime の `DATABASE_URL` とは分離し、`DATABASE_URL_UNPOOLED` の direct connection を使用する。`DATABASE_URL_UNPOOLED` が未設定の場合に `DATABASE_URL` へ fallback しない。

Preview / Production の maintenance operation では、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に期待する接続先 identity を設定する。これらは接続先を照合するための host / database 名であり DB credential ではない。接続文字列の host / database が期待値と一致しない場合、Neon の pooled endpoint が指定された場合、または接続後の `current_database()` が一致しない場合は、advisory lock や書き込みを開始せず停止する。接続先を推測して続行せず、設定を確認・修正してから再実行する。

remote PostgreSQL へ接続する場合は TLS 証明書検証を有効にし、`sslmode=verify-full` を利用する。localhost や Testcontainers など TLS を使用しないローカル接続では、この指定を前提としない。

DB schema と migration の Source of Truth は `packages/db` とする。

ローカル migration:

```sh
pnpm db:migrate
```

ローカルから実行する migration は Local DB だけを対象とし、共有 Preview DB や Production DB をローカル操作の対象にしない。対象 DB を必ず確認してから実行する。適用済み migration の内容を書き換えて履歴を変更せず、schema 変更には新しい migration を追加する。

### Production DB backup

Production DB は Neon の短期復旧機能だけに依存せず、GitHub Actions の `.github/workflows/backup-production-db-scheduler.yml` と `.github/workflows/backup-production-db.yml` を組み合わせて Cloudflare R2 へ論理バックアップを保存する。

`Production DB Backup Scheduler` は毎日 03:17（Asia/Tokyo）に動作し、`main` を ref として `Production DB Backup` を `workflow_dispatch` する。scheduler 自身は Production DB や R2 の credential を参照しない。実際の backup job は `main` の workflow revision だけで実行し、`production` Environment の credential を使用する。`Production DB Backup` は必要に応じて `main` を選択して手動実行できる。backup job は PostgreSQL 18 の `pg_dump` で custom-format dump を作成し、`pg_restore --list` で archive として読み取れることを確認し、SHA-256 checksum を生成してから R2 へ upload する。保存先 key は UTC 基準の `production/YYYY/MM/DD/timecard-<timestamp>.dump` とし、同じ key に `.sha256` を付けた checksum file も保存する。upload 後は R2 object の ContentLength と local dump size が一致することを確認する。

#### Cloudflare R2

1. Production DB backup 専用の R2 bucket を作成し、公開アクセスを有効にしない。
2. bucket の Object Lifecycle Rule で prefix `production/` の object を 30 日後に expire する。dump と `.sha256` は同じ prefix にあるため同じ retention を適用する。
3. workflow 専用 R2 API token を作成し、権限を Object Read & Write、対象をこの backup bucket のみに限定する。bucket 作成や Lifecycle Rule 変更を行える管理権限は付与しない。
4. token 作成時に取得した Access Key ID / Secret Access Key と Cloudflare Account ID、bucket 名を GitHub 側へ登録する。実値は repository や文書へ記録しない。

#### PostgreSQL backup role

Production DB の通常 application credential を GitHub Actions へ複製せず、backup 専用 login role `timecard_backup` を使用する。

Production database owner で次を実行する。password は十分に強いランダム値を生成し、実値を shell history、Issue、文書へ残さない。

```sql
CREATE ROLE timecard_backup LOGIN PASSWORD '<generated-strong-password>';
GRANT CONNECT ON DATABASE neondb TO timecard_backup;
GRANT pg_read_all_data TO timecard_backup;
ALTER ROLE timecard_backup SET default_transaction_read_only = on;
```

`timecard_backup` に SUPERUSER、CREATEDB、CREATEROLE、REPLICATION、BYPASSRLS や個別の書き込み権限を追加しない。現行 schema は RLS を使用していない。将来 RLS を導入する場合、`pg_read_all_data` は RLS を bypass しないため、backup role から全対象行を dump できることを改めて検証する。

Neon Console で role に `timecard_backup`、database に `neondb`、direct connection を選び、TLS 証明書検証を有効にした `sslmode=verify-full` の接続文字列を取得する。この実値を GitHub Environment `production` の Secret `PRODUCTION_DATABASE_BACKUP_URL` として保存する。

#### GitHub Actions 設定

GitHub Environment `production` の Secrets:

- `PRODUCTION_DATABASE_BACKUP_URL`: `timecard_backup` で Production `neondb` へ接続する direct connection string
- `R2_BACKUP_SECRET_ACCESS_KEY`: backup bucket のみに scope した R2 Secret Access Key

GitHub Environment `production` の Variables:

- `R2_BACKUP_ACCESS_KEY_ID`: 対応する R2 Access Key ID
- `R2_BACKUP_BUCKET`: Production DB backup 用 bucket 名

Repository Variables:

- `R2_BACKUP_ACCOUNT_ID`: Cloudflare Account ID

Production 固有の 2 つの Secret（`PRODUCTION_DATABASE_BACKUP_URL`、`R2_BACKUP_SECRET_ACCESS_KEY`）と 2 つの Variable（`R2_BACKUP_ACCESS_KEY_ID`、`R2_BACKUP_BUCKET`）は、Repository scope に重複登録しない。

初期設定後は GitHub Actions の `Production DB Backup` workflow で ref に `main` を選んで手動実行し、成功した run が R2 に `.dump` と対応する `.dump.sha256` を作成することを確認する。default branch の選択状態をそのまま信用せず、実行前に `main` であることを確認する。object が存在するだけでは restore 可能性の確認にはならないため、初回 restore 検証は [運用保守手順書](./運用保守手順書.md) のバックアップ・復旧手順に従う。

## 5. LINE Login / LIFF

staff と `/admin` は LINE Login / LIFF から認証情報を取得し、Server Action から `packages/users` の authentication application へ渡す。`apps/web` の Composition Root が LINE 検証 adapter と PostgreSQL adapter を組み立て、本システムのセッションを作成する。

内部業務処理は同じ Next.js アプリ内の Server Components / Server Actions から server application を直接利用するため、別 API origin、CORS 用の許可 origin、ブラウザ向け業務 API base URL は設定しない。具体的な設定項目は `apps/web/.env.example`、root `.env.local.example`、各 env 定義を Source of Truth とし、Vercel またはローカル `.env` へ設定する。

### staff で実 LINE 認証を使うローカル開発

staff を実際の LINE アカウントで認証しながらローカル確認する場合は、Production / 公開中の LIFF アプリとは別に、ローカル専用の LIFF アプリを使用する。LINE Login Channel は既存の開発用 Channel を利用できるが、ローカル用 LIFF アプリ自体は共有 Preview や公開中の LIFF アプリと分離し、Endpoint URL を `https://localhost:3000` に固定する。

ローカル確認では次の経路を使用する。

```text
ローカル専用 LIFF
  ↓
https://localhost:3000
  apps/web (Next.js HTTPS)
  ├─ staff
  ├─ /admin
  └─ Server Components / Server Actions
       ↓
Local / 開発専用 DB
```

内部業務処理のために別 API process、開発用 proxy、port 8787 は使用しない。ブラウザから汎用的な same-origin REST API を呼び出す構成にも戻さない。ローカル開発のために本番の認証方式や session cookie のルールを緩和しない。

#### 初回セットアップ

1. 開発用 LINE Login Channel にローカル専用 LIFF アプリを用意する。共有 Preview や Production / 公開中の LIFF アプリを流用しない。
2. LINE Developers でローカル専用 LIFF アプリの Endpoint URL を `https://localhost:3000` に設定する。ローカル専用アプリとしてこの値を固定し、日常の起動時には変更しない。
3. `mkcert` をインストールし、ローカル CA を初期化する。

   ```sh
   mkcert -install
   ```

4. リポジトリ root で localhost 用証明書を作成する。

   ```sh
   mkcert localhost
   ```

   `localhost.pem` と `localhost-key.pem` は Git 管理しない。

5. Production / 共有 Preview ではない Local または開発専用 DB を用意する。実運用データは使用しない。
6. root の `.env.local.example` を `.env.local` としてコピーし、ローカル用の値を設定する。

   ```sh
   cp .env.local.example .env.local
   ```

   主な設定は次のとおり。

   - `DATABASE_URL`: Local または開発専用 DB
   - `DATABASE_ENVIRONMENT=local`（runtime は node-postgres で接続する）
   - `LINE_CHANNEL_ID`: ローカル専用 LIFF アプリが属する開発用 LINE Login Channel
   - `NEXT_PUBLIC_LIFF_ID`: ローカル専用 LIFF アプリの LIFF ID

   内部業務処理は `apps/web` 内の Server Components / Server Actions から実行するため、ローカル用の業務 API base URL や別 API port は設定しない。

#### 日常の起動

初回セットアップ後は root で次を実行する。

```sh
pnpm dev:web:local
```

launcher は root `.env.local` と localhost 証明書を検証し、Local DB migration の成功後に `apps/web` を `https://localhost:3000` で起動する。staff、`/admin`、Server Components / Server Actions はこの 1 つの Next.js process から提供される。root の mkcert 証明書を使って HTTPS で直接起動するため、日常の起動時に LINE Developers の Endpoint URL を変更する必要はない。

起動後は `https://liff.line.me/<NEXT_PUBLIC_LIFF_ID>` を開き、実際の LINE ログインを完了する。認証後に本システムの staff 画面が認証済み状態になり、勤怠データを取得できることを確認する。書き込みを含む確認が必要な場合は打刻も実施し、session cookie と Server Action の経路で正常に完了することを確認する。

実 LINE ログインは手動確認用であり、Playwright 等の自動 E2E では従来どおり fake / mock を使用する。

## 6. Vercel

`apps/web` を単一の Vercel deploy 単位として扱う。staff、`/admin`、Server Components / Server Actions のために個別の Vercel project や別 origin を用意しない。

`apps/web/vercel.json` と root package scripts を Source of Truth とし、Vercel 側の設定、Build Command、環境変数を一致させる。

`develop` は GitHub Actions の Quality 成功後に Preview へ反映する。`main` は Production deployment の反映元 branch とし、同じ Quality workflow で検証された revision だけを Production deployment の対象とする。リリース作業で使用する `release/<version>` branch と `main` の関係は [CONTRIBUTING.md](../CONTRIBUTING.md) の Branch / Merge ルールを Source of Truth とする。Production 環境は既に構築済みであり、`main` からの Quality、Production deployment、実 LINE / LIFF を含む一気通貫の実環境確認も完了している。過去の確認実績を現在の反映先とみなさず、運用時は現在の Quality 済み SHA、Vercel deployment、public alias の対応を都度確認する。

### develop Preview

`develop` push では Vercel の Git 連携による自動 deployment を開始しない。GitHub Actions の `Quality` workflow で `quality` job が成功した後、runtime 非影響変更のみと判定された場合は Preview deployment を作成しない。runtime への影響がある場合、または安全に非影響と判断できない場合は、`deploy-preview` job が検証済みの `github.sha` を指定して Vercel Deployment API から Preview deployment を作成する。

`deploy-preview` job は複数 run の deployment を同時実行せず待ち行列へ入れる。deployment slot を取得した時点で remote `develop` の HEAD とその run の `github.sha` を再比較し、一致しない superseded run は deployment を開始せず正常に skip する。これにより、Quality の完了順が push 順と前後しても古い run が新しい `develop` Preview を巻き戻さない。

deployment の source は Quality で検証した exact SHA と `develop` ref に固定する。Preview 用環境変数、`apps/web/vercel.json` の build command、migration flow、Vercel が管理する `develop` branch alias は従来どおり Vercel 側で適用する。GitHub Actions 側へ Preview DB や application runtime の secret を複製しない。

GitHub Actions の Repository Secret として、Preview deployment 起動用に次を設定する。

- `VERCEL_TOKEN`

GitHub Actions の Repository Variables として、次を設定する。

- `VERCEL_ORG_ID`
- `VERCEL_PROJECT_ID`

`VERCEL_ORG_ID` と `VERCEL_PROJECT_ID` は認証情報ではなく識別子であるため、Repository Variables として扱う。

`VERCEL_TOKEN` の実値は文書、repository、workflow log へ記載しない。

Quality と Preview deployment は別の結果として扱う。Quality が成功しても Vercel deployment が失敗した場合は `deploy-preview` job が失敗し、GitHub Actions の job 結果と Vercel 側の deployment status から確認する。

この経路は Preview 専用であり、Production deployment は次節の `main` 用経路と分離して扱う。

### Production

Production 環境は既に構築済みであり、Production deployment の反映元 branch は `main` とする。旧 `master` は Production migration / deployment の許可 branch として扱わない。

`main` push では GitHub Actions `Quality` workflow の `quality` job を先に実行し、成功した場合だけ `deploy-production` job を起動する。Quality 失敗 revision は Production deployment の対象にならない。

`deploy-production` は Quality が検証した `${{ github.sha }}` を exact revision として checkout する。deployment slot 取得後に remote `main` HEAD を再確認し、HEAD がその SHA から進んでいる superseded run は deployment を開始せず正常に skip する。

Production deployment は `main-production-deploy` concurrency group で直列化し、複数の Production deployment を同時実行しない。

Production runner は `scripts/deploy-vercel-production.mjs` とする。runner は `GITHUB_REF_NAME=main`、40 桁の exact `GITHUB_SHA`、checkout HEAD、clean working tree、GitHub repository identity、Vercel project identity / Git link を検証してから Vercel Deployment API を呼ぶ。

Vercel deployment の source は `main` と Quality 済み exact SHA に固定し、`target: production` で作成する。CI で生成済みの prebuilt artifact を Production へ配布する方式にはしない。

Production deployment 作成時は Vercel Build Cache を再利用しない force build (`forceNew`) とし、過去の build cache を Production build の成立条件にしない。一方、develop / Preview の cache 方針は変更しない。

runner は deployment が `READY` になるまで待機し、その後に Production target、project、GitHub repository、`main` ref、exact SHA の metadata を再検証する。これらが一致しない場合は成功扱いにしない。

`deploy-production` が利用する GitHub Actions 側の credential / identifier 名は既存の `VERCEL_TOKEN`、`VERCEL_ORG_ID`、`VERCEL_PROJECT_ID` とする。実値は文書・repository・workflow log に記載しない。application runtime や Production DB の secret をこの deployment 起動用設定と混同しない。

Quality と Production deployment は別 job / 別結果として扱う。Quality が成功していても Production build、migration、Vercel deployment、READY / metadata 検証のいずれかが失敗すれば `deploy-production` は失敗として確認する。

Production deployment が失敗した場合、Quality の成功自体を書き換えない。GitHub Actions の `deploy-production` job と Vercel 側 deployment status を確認して原因を切り分ける。superseded run の正常 skip と deployment failure を混同しない。

#### 現在の Production 反映先の確認

現在公開されている revision を確認するときは、GitHub の branch HEAD、CI の成功、Vercel deployment、public alias を別々の情報として確認し、同じ revision を指していることを照合する。

1. GitHub の `main` で対象となる exact SHA を確認する。
2. GitHub Actions `Quality` workflow で、その SHA の `quality` job と `deploy-production` job が成功していることを確認する。
3. `deploy-production` job の結果から Vercel Production deployment を特定し、runner が出力した `ref: main` と SHA が対象 revision と一致することを確認する。
4. Vercel 側で対象 deployment が `READY`、Production target、Git source が対象 repository の `main`、source SHA が同じ exact SHA であることを確認する。
5. Production の public alias / domain がその deployment を指していることを確認する。deployment が `READY` であることだけを、現在 public traffic がその deployment へ向いている証拠として扱わない。
6. release 内容に応じて staff、`/admin`、実 LINE / LIFF 等の必要な smoke test を行う。

Production の初回構築と一気通貫の実環境確認は Issue #116 で完了済みである。Issue #116 に残された過去の deployment ID や SHA は確認実績の記録であり、現在の Production 反映先を示す固定値として使用しない。

Vercel project、Production DB、LINE / LIFF、GitHub Actions / Vercel の設定を変更した場合は、変更した境界について現在値を再照合し、その後の Production release で必要な smoke test を再実施する。初回構築作業を通常の未完了タスクとして扱わない。

## 7. Web deployment と migration

`apps/web` の deployment では、必要な migration を Web build より前に適用する。migration はアプリケーション起動時や HTTP リクエスト処理中には実行せず、デプロイ処理上の明示的な step として扱う。

```text
環境ガード
  ↓
Maintenance DB 接続設定の検証
  ↓
接続先 DB identity の検証
  ↓
PostgreSQL advisory lock
  ↓
Drizzle migration
  ↓
Web build
```

`apps/web/vercel.json` の build command は migration gate の成功後に root の `build:web` を実行する。

現在の `apps/web/vercel.json` の Production build でも、`pnpm --filter @repo/db migrate:deploy` が成功した後に `pnpm -w build:web` が実行される契約を維持する。

DB migration command は Node.js の `development` export condition を有効にして `tsx` で実行する。これにより、migration から直接利用する workspace package は build 済み `dist` ではなく source export へ解決される。

この deployment pipeline では migration step が DB 接続設定を必要とするが、それは migration を実行するための deploy-time requirement であり、Web build artifact 自体の build-time requirement とは区別する。

Preview / Production の deploy migration では、maintenance 用 direct connection として `DATABASE_URL_UNPOOLED` を設定し、対象確認用に `DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` を設定する。通常 runtime が利用する `DATABASE_URL` は別の契約として維持し、maintenance connection の代替には使用しない。

`DATABASE_URL_UNPOOLED` は credential を含む secret として管理する。期待 host / database は接続先 identity として設定する。これらが欠落している、接続文字列が Neon pooled endpoint である、期待 host / database と一致しない、または接続後の database が一致しない場合、migration は advisory lock や schema 変更へ進む前に失敗する。

- deploy 時はリポジトリへコミット済みの migration だけを順番に適用し、schema 差分から migration を自動生成しない。
- 共有 Preview DB への deploy migration は `develop` からだけ実行し、feature / bugfix 等の作業ブランチから適用しない。
- 実行環境と migration 対象 DB の対応を安全に特定できない場合は、推測して続行せず停止する。
- Production DB への deploy migration は、Vercel Production context、`main` branch、`DATABASE_ENVIRONMENT=production` が一致する Production release だけで許可する。旧 `master`、Local、Preview、その他の branch / environment の組み合わせは fail closed で拒否する。
- migration の同時実行は advisory lock で抑止する。
- migration 失敗時は deployment を成立させない。
- migration 適用後に build が失敗しても DB を自動 rollback する前提にはしない。

migration 成功後に Web build または deployment が失敗すると、DB schema だけが先に進む場合がある。Application rollback は DB schema や保存済み Event を巻き戻さないため、旧 revision が現在の schema / Event format と互換であることを確認してから行う。互換性を確認できない場合は rollback を強行しない。

Application rollback、roll forward、DB restore、Projection rebuild の使い分けと復旧手順は [運用保守手順書](./運用保守手順書.md) を Source of Truth とする。schema 変更では migration 適用後に旧版または新版の application が動く時間帯を考慮し、必要な backward compatibility と安全なデプロイ順序を設計する。

### Attendance Current State Projection の rebuild

Current State Projection は Event Store から再生成可能な派生データであり、Event Store を Source of Truth とする。Local では root の `.env.local` に Local 用設定を置いたうえで、明示的に次を実行する。

```sh
pnpm --filter @repo/server projection:rebuild:local
```

Preview の rebuild は Vercel の build command へ組み込まない。Preview 初回導入では、Projection を維持でき、not-ready 状態を安全に扱える application version が active deployment へ切り替わったことを先に確認してから、post-deploy の明示的な maintenance operation として実行する。

実行前に、Preview DB の direct connection を `DATABASE_URL_UNPOOLED` として現在の shell に secret 設定し、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に対象 Preview DB の identity を設定する。あわせて `DATABASE_ENVIRONMENT=preview` と `ATTENDANCE_PROJECTION_REBUILD_CONFIRM=preview` を一時的に設定する。`DATABASE_URL_UNPOOLED` が無い場合に通常 runtime の `DATABASE_URL` へ fallback しない。その状態で次を実行する。

```sh
pnpm --filter @repo/server projection:rebuild:preview
```

Production の rebuild も Vercel の build command へ組み込まない。Event Store が正常な Source of Truth として利用でき、Current State Projection の欠損・不整合または not-ready 状態を解消する必要がある場合だけ、明示的な maintenance operation として実行する。実行前に、現在 active な application が rebuild 中の not-ready 状態を安全に扱えることを確認する。

実行前に、Production DB の direct connection を `DATABASE_URL_UNPOOLED` として現在の shell に secret 設定し、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に対象 Production DB の identity を設定する。あわせて `DATABASE_ENVIRONMENT=production` と `ATTENDANCE_PROJECTION_REBUILD_CONFIRM=production` を一時的に設定する。`DATABASE_URL_UNPOOLED` が無い場合に通常 runtime の `DATABASE_URL` へ fallback しない。その状態で次を実行する。

```sh
pnpm --filter @repo/server projection:rebuild:production
```

Production rebuild は Vercel の build / runtime 内では実行せず、Vercel environment と判定されない運用者の shell から明示的に実行する。Projection rebuild は Event Store から派生データを再生成する操作であり、原本データが破損・欠損している場合の DB restore の代替には使用しない。

Preview / Production rebuild は direct maintenance connection、期待 host / database、対象 environment、確認値をすべて照合できた場合だけ開始する。接続情報の実値は文書、Issue、command example、ログへ記載しない。復旧判断と restore 手順は [運用保守手順書](./運用保守手順書.md) を参照する。

## 8. Sentry / ログ

必要な環境では Sentry を有効化する。DSN、auth token、組織・プロジェクト設定等の実値は secret として管理する。

Vercel の deployment / runtime log と Sentry を用途に応じて確認する。アプリケーション独自の request log を稼働確認のためだけに維持しない。

## 9. デプロイ前後の確認

### デプロイ前

- 対象 branch / commit が正しい。
- 必要な環境変数が対象環境に設定されている。
- schema 変更がある場合、対応 migration が存在する。
- `pnpm quality` が成功している。
- 必要な場合 Large Test を実施している。
- Production の場合、release 対象が `main` の Quality 成功済み revision であることを確認する。
- Production の場合、Production DB / runtime secret / Vercel project 等の対象環境設定が揃っていることを確認する。
- Production deployment を手動で別 SHA に差し替えず、GitHub Actions の exact revision 経路を使う。

### デプロイ後

- 通常の staff 入口と `/admin` で認証と主要画面の初期表示を確認できる。
- 変更内容に対応する主要操作が成立する。
- 監視に新しい unexpected error がない。
- Production の場合、`deploy-production` job が成功し、Vercel deployment が `READY` であることを確認する。
- Production の場合、runner が検証した source ref が `main`、source SHA が Quality 済み revision と一致することを確認する。
- Production の初回一気通貫確認は Issue #116 で完了済みである。各 release では現在の public alias が意図した deployment / SHA を指していることを確認し、変更内容に応じた smoke test を実施する。LINE / LIFF、DB、Vercel 等の Production 設定を変更した場合は、その境界も再確認する。
