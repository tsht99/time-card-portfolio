# 要件定義書

## 1. 文書の役割

本書は、本システムが満たすべき業務上・システム上の要求を定義する。

利用者・業務・外部から観測可能な振る舞い・制約を中心に記載し、内部モジュール、ファイル、関数、DB クエリなどの実装詳細は扱わない。実現方式は [設計書](./設計書.md) を参照する。

## 2. 背景・目的

店舗・小規模事業者における勤怠管理では、打刻忘れ・誤入力、管理者による不備確認、曜日や勤務区分による時給管理、変更履歴の追跡などに負担が生じる。

本システムは、スタッフと管理者が Web 画面から勤怠を扱い、記録・訂正・集計・履歴確認を一貫して行える状態を目指す。

主な目的は次のとおり。

- スタッフが日々の出勤・退勤を簡単に記録できること
- 当日中の打刻忘れは現在状態と矛盾しない範囲でスタッフが正しい当日時刻を指定した通常打刻で対応し、前日以前の打刻忘れや登録済み勤怠の修正は管理者が確認済みの正しい日時で対応すること。確認できない日時を推測して保存しないこと
- 勤怠の打刻誤りを、変更経緯を追跡できる形で訂正・取消できること
- 管理者が利用者横断で勤怠状態と不備を把握できること
- 時給履歴に基づいて月次の給与見込みと算定上の不足を確認できること
- 認証・認可・競合検知により不正または矛盾する変更を防ぐこと

## 3. 利用者

| 利用者            | 主な目的                                                                   |
| ----------------- | -------------------------------------------------------------------------- |
| スタッフ（staff） | 出勤・退勤、当日の状態確認、自身の勤怠履歴確認                             |
| 管理者（admin）   | ユーザー管理、勤怠一覧・履歴確認、訂正・取消、時給管理、給与一覧・給与詳細 |
| システム運用者    | デプロイ、障害確認、データ保全、監視、復旧対応                             |

本書では、`staff` ロールの利用者を「スタッフ」と呼ぶ。

本システムの利用者は少なくとも `staff` と `admin` のロールを持つ。管理系操作は管理者だけに許可する。

スタッフの利用状態は、LINE 本人確認済み・利用承認待ちの `pending`、利用可能な `active`、利用停止中の `inactive` を区別する。LINE で本人確認できることと本システムの利用を許可されていることは別に扱い、未登録のスタッフは管理者の承認なしに利用を開始できないこと。

## 4. 対象範囲

現行システムは主に次を対象とする。

1. LINE 認証情報を利用したログイン
2. スタッフ向け勤怠 Web UI
3. 管理者向け管理 Web UI
4. 出勤・退勤の記録
5. 管理者による未登録勤怠の新規作成、および勤怠の訂正・取消
6. 勤怠の変更履歴管理
7. 勤怠一覧・当日状態・月別履歴の参照
8. スタッフの利用状態管理
9. 利用者別・勤務区分別・曜日/祝日別の時給履歴管理
10. 月次の給与見込み・算定上の不足確認
11. 稼働状態確認、ログ、エラー監視などの運用機能

次は対象外とする。

- LINE 公式アカウント、Messaging API、リッチメニューを本システムの利用入口として提供すること
- 税・社会保険・源泉徴収・法定割増・給与明細などを含む給与計算全般
- 給与振込データの生成
- シフト作成・シフト募集
- 有給休暇や各種申請の承認ワークフロー
- 月次締め・締め解除
- Event Store の Archive / retention / Compaction などのデータ削減

本システムの給与集計は、勤務分数と設定時給に基づく勤怠上の集計値とする。

## 5. 機能要件

### 5.1 認証・セッション

- staff/admin は LINE の認証情報を利用して本人確認できること。
- LINE 本人確認の成功だけを本システムの利用許可として扱わないこと。
- LINE 本人確認に成功した未登録のスタッフは `pending` として登録し、管理者に承認されるまで本システムのセッションを持てないこと。
- 初回登録時には、LINE から取得した表示名の前後空白を除いた値が 1〜100 文字であれば 本システム上の表示名の初期値として利用できること。文字種は制限しない。
- LINE から取得した表示名が空白のみ、または 101 文字以上の場合も本人確認と承認待ち登録を成立させ、業務用表示名は未設定として管理者が設定できること。長い値を切り詰めて保存しないこと。
- 既存利用者が再認証しても、LINE 側の表示名によって 本システム上の表示名を自動更新しないこと。
- `pending` のスタッフが承認前に再認証しても利用状態を自動的に `active` へ変更しないこと。
- LINE 認証自体の失敗と、LINE 本人確認には成功したが利用承認待ちである状態を利用者が区別できること。
- `active` の利用者は認証成立後に継続利用可能なセッションを持てること。
- セッションの期限切れ・失効時は再認証が必要であることを利用者が判別できること。
- `inactive` のスタッフは 本システムを継続利用できず、新しいセッションも作成できないこと。
- staff を `inactive` にした後に再度 `active` にしても、利用停止前または利用停止と競合して開始された古いセッションを再利用できないこと。

### 5.2 スタッフ向け勤怠

- 当日の昼・夜それぞれの勤怠実績を確認でき、同一勤務日・同一勤務区分に複数の勤怠がある場合も全件を確認できること。
- 現在勤務中の勤怠を確認できること。
- 現在勤務中の勤怠が存在しない場合は、同じ勤務日・同じ勤務区分に完了済み勤怠が存在していても新しい出勤を開始できること。
- 同一勤務日・同一勤務区分の勤怠件数に上限を設けないこと。
- 現在の勤務状態を確認しながら、出勤・退勤という実際の操作意図を選べること。
- 現在状態と操作意図が矛盾しない場合は通常打刻として記録し、実際の打刻時刻を指定できること。
- スタッフは通常打刻で時刻だけを指定し、日付は指定できないこと。
- 指定時刻は操作時点の JST 日付の時刻として扱うこと。
- 未勤務状態では正しい当日時刻を指定して通常出勤できること。
- 勤務中状態では正しい当日時刻を指定して通常退勤できること。
- 未勤務状態から退勤した場合は保存せず、出勤していない旨のエラーを表示すること。
- 勤務中状態から新しい出勤を行った場合は保存せず、退勤していない旨のエラーを表示すること。
- 状態矛盾時にスタッフ専用の Recovery dialog / bundled recovery へ遷移しないこと。
- スタッフは前日以前の日付を通常打刻として指定できないこと。
- 前日以前の打刻忘れは管理者が対応すること。
- 前日から継続している勤務中勤怠は、操作当日の正しい退勤時刻で通常退勤できること。
- 日付変更だけでは勤務中勤怠を終了しないこと。
- 欠けた日時や前日の退勤日時を自動推測しないこと。
- 通常退勤は確認済み Attendance ID / Version を対象とし、保存前に対象が変わっていた場合は別 Attendance へ自動差し替えず、最新状態の再取得を求めること。
- 月を指定して自身の勤怠履歴を確認できること。
- 登録済み勤怠は当日分を含め staff では閲覧専用とし、staff 本人は事後の訂正・取消を実行できないこと。
- 登録済み勤怠の訂正・取消が必要な場合は admin が対応できること。
- 前日以前から継続している勤務中勤怠も staff から訂正・取消はできないが、通常の退勤はできること。

### 5.3 管理者向け勤怠

- 利用者横断の勤怠一覧を確認できること。
- 勤怠一覧は勤務日ごとにまとめ、同じ勤務日内では利用者・勤務区分に関係なく出勤時刻の降順で表示すること。通常勤怠と取消済み勤怠を同じ並び順で扱うこと。
- 勤怠一覧では通常・取消済みを判別でき、退勤時刻は勤務日基準で翌日を 24 時間超表記できること。未登録勤怠の新規作成導線を一覧から提供すること。
- 必要に応じてユーザー、期間、勤務区分、状態で絞り込めること。
- 管理者は、出勤・退勤の実績日時が判明している未登録勤怠について、対象となるスタッフまたは管理者本人、勤務区分、出勤日時、退勤日時を指定して新規作成できること。新規作成の対象者には利用中・利用停止中のスタッフと管理者本人を選べるが、他の管理者および承認待ちの利用者は選べず、直接要求しても作成できないこと。
- 新規作成する勤怠の勤務日は独立して指定せず、出勤日時の日本時間（Asia/Tokyo）の日付として決定すること。
- 管理者は、確認できた正しい日時だけを新規作成・訂正・勤務中勤怠への退勤補記として保存すること。
- 管理者は勤務中勤怠に確認済みの退勤日時を補記し、完了済み勤怠にできること。
- 正しい日時が確認できない場合は、現在時刻、操作日、勤務区分、シフト等から日時を推測して保存しないこと。
- 管理者が新規作成した勤怠は通常の勤怠として扱い、勤怠一覧・給与一覧へ反映し、その後は変更権限の範囲内で訂正・取消を行えること。
- 管理者による新規作成の操作は、勤怠の変更履歴から操作者を追跡できること。
- 同一利用者・同一勤務日・同一勤務区分の既存勤怠があることだけを理由に新規作成を拒否しないこと。
- 同一利用者の確定した勤務時間帯と重複する勤怠の新規作成は拒否すること。
- 新規作成を拒否した場合に、出勤だけが記録された不完全な新規勤怠を残さないこと。
- 勤怠の変更履歴を確認できること。
- 権限の範囲内で勤怠を訂正・取消できること。
- 管理者は、スタッフおよび自分自身の勤怠を訂正・取消できる一方、他の管理者の勤怠を訂正・取消できないこと。退勤日時の補記と勤怠全体の取消も同じ変更権限に従うこと。
- 取消は Attendance 全体を取消済みにする不可逆な操作とし、出勤だけ・退勤だけの部分取消を提供しないこと。
- 退勤済み Attendance の退勤日時を未登録状態へ戻す操作を提供しないこと。誤って早く退勤した場合は、実際の勤務終了後に admin が確認済みの正しい退勤日時へ訂正すること。
- 取消済み Attendance は訂正・再取消・復活できないこと。
- 他の管理者の勤怠一覧・詳細・変更履歴は閲覧できるが、訂正・取消・退勤補記はできないこと。共通の変更権限は 6.4 に従うこと。
- 訂正後に同一利用者・同一勤務日・同一勤務区分の勤怠が複数になることだけを理由に訂正を拒否しないこと。
- 訂正によって同一利用者の確定した勤務時間帯が既存勤怠と重複する場合は、その訂正を拒否すること。

### 5.4 ユーザー管理

- 管理画面の「ユーザー」タブから開くユーザー一覧とユーザー詳細では、staff と admin の双方を確認でき、管理者とスタッフを区別して表示できること。
- ログイン中の管理者本人を他の管理者と区別でき、管理者が複数いる場合もそれぞれ確認できること。
- 管理者は `pending`、`active`、`inactive` のスタッフを、画面上ではそれぞれ「承認待ち」「利用中」「利用停止」と判別でき、内部状態値の理解を前提としないこと。
- 管理者は承認待ち・利用中・利用停止のスタッフを確認し、表示名編集および現在状態に応じた承認・利用停止・再有効化を実行できること。
- 利用状態を変更する前に、対象スタッフ、現在の状態、変更後の状態を 本システムの画面内で確認してから確定でき、ブラウザ標準の確認 UI に依存しないこと。
- 本システム上の利用者の表示名は、初回登録後は LINE プロフィールから独立した業務用名称として扱うこと。
- 管理者は `pending`、`active`、`inactive` のいずれの staff についても表示名を変更できること。
- 管理者はユーザー詳細画面で自分自身の表示名を設定・変更でき、表示名が未設定でも本人が設定できること。
- 管理者は他の管理者の表示名を変更できず、画面を迂回して直接変更を要求した場合も拒否されること。
- 管理者が変更する表示名は前後の空白を除いた後に 1〜100 Unicode コードポイントであること。文字種は制限しない。
- `pending` の staff は、業務用表示名が未設定でも承認待ちとして保持できること。
- `active` と `inactive` の staff は、前後の空白を除いた後に空でない業務用表示名を必ず持つこと。
- `active` と `inactive` の利用者を合わせた集合では、null でない表示名を重複させないこと。
- `pending` 同士、および `pending` と `active / inactive` の間では表示名の重複を許容すること。
- `pending -> active` または `inactive -> active` の変更時に表示名が未設定または前後の空白を除いた後に 1〜100 文字の範囲外の場合は、利用状態の変更を成立させず、管理者が有効な表示名を設定する必要があることを判別できること。
- `pending -> active` または `inactive -> active` の変更時に表示名の重複が生じる場合は、利用状態の変更を成立させないこと。
- `active / inactive` の staff または管理者本人の表示名変更で、他の `active / inactive` 利用者と重複する場合は、表示名の変更を成立させないこと。
- 管理者だけが `pending` のスタッフを `active` へ変更して利用を承認できること。
- 承認されたスタッフは、その後の LINE 認証によって本システムの利用を開始できること。
- `pending` から `inactive` へ変更できないこと。
- `active` と `inactive` は相互に変更できること。
- `active` または `inactive` から `pending` へ変更できないこと。
- staff を `inactive` にした場合、その staff の既存セッションを継続利用できないこと。
- admin の利用状態はユーザー詳細画面から変更できず、staff 向けの承認・利用停止・再有効化の対象にもできないこと。
- 管理者本人の表示名を変更しても利用者 ID および勤怠変更履歴に記録済みの操作者 ID は維持し、勤怠変更履歴ではその操作者を変更後の表示名で確認できること。

### 5.5 時給管理・給与

- 管理者はユーザー詳細から開いた時給設定画面で、URL に指定された対象ユーザーを識別できること。時給設定画面に別ユーザーへの切替操作を設けないこと。
- 管理者はスタッフと自分自身の時給を確認・変更でき、他の管理者の時給は閲覧のみとすること。登録済みルールの訂正・削除は時給履歴画面で行い、共通の変更権限は 6.4 に従うこと。
- 時給ルールは昼/夜、曜日または祝日、適用開始日を区別できること。
- ユーザー詳細から時給設定を開くと、対象ユーザー切替操作を挟まず、その利用者の時給設定を確認できること。別ユーザーの設定はユーザー一覧から対象ユーザーの詳細を開いて確認すること。
- 選択した利用者について、現在または登録済みの適用開始日を選び、その時点で有効な時給を月曜日から日曜日および祝日を行、昼/夜を列とする一覧で確認できること。
- 勤怠詳細から時給設定を開く場合は、対象利用者と勤怠日を URL で引き継ぎ、その日時点で有効な時給を初期表示できること。直接 URL を開いた場合や再読み込み後も同じ確認日を復元できること。
- 時給未設定の勤怠からも同じ導線を利用でき、変更権限がある場合は引き継いだ勤怠日を適用開始日の初期値として時給改定へ進めること。
- 時給設定画面から対象利用者の時給履歴を開き、登録済みルールを適用開始日ごとの変更前後として確認・訂正・削除できること。履歴は曜日・昼夜の絞り込みを設けず、将来と今日以前の変更を分けて示すこと。
- 日本時間の現在時点、対象利用者が持つ適用開始日、勤怠詳細から引き継いだ確認日について、その時点で有効な時給を確認できること。
- 曜日・勤務区分ごとに、選択日以前に適用が開始されたルールのうち最も新しいルールを選び、時給を表示すること。
- 有効な時給ルールがない場合は未設定と表示し、設定済みの 0 円と区別できること。
- 時給設定画面は時給の閲覧と新しい改定の一括登録を担い、単一セルの変更にも個別操作を設けないこと。
- 時給一覧では、共通の適用開始日を指定して複数の曜日・昼夜セルを一括編集し、変更セルだけを 1 回の原子的な保存で反映できること。空欄は変更なしとし、0 円を有効な変更値として扱うこと。
- 将来適用される時給ルールと、今日以前に適用されるルールを判別できること。
- 管理者は時給履歴画面で登録済みルールの時給、勤務区分、曜日/祝日区分、適用開始日を訂正できること。
- 同一条件・同一適用開始日の重複ルールを生じる登録・編集はできないこと。
- 管理者は時給履歴画面で削除対象の勤務区分、日区分、時給、適用開始日を確認したうえで、特定の時給ルールを削除できること。
- 管理者は給与一覧の対象月を直接選択でき、前月・翌月へ移動できること。
- 対象月の利用者別集計を確認できること。
- 給与集計では、利用者ごとに月間勤務時間、給与見込み、不完全勤怠件数、時給未設定件数を算出すること。一覧画面では利用者名、給与見込み、必要な状態表示を確認できること。
- 勤務時間を算出できない不完全勤怠は、月間勤務時間と給与見込みへ含めないこと。
- 勤務時間を算出できても時給を決定できない勤怠は、月間勤務時間には含め、給与見込みには含めないこと。
- 同一勤務日・同一勤務区分に複数の勤怠がある場合も、対象となる各勤怠を月間勤務時間および給与見込みの対象として扱うこと。
- 給与見込みは、各勤怠日の勤務区分、曜日/祝日、適用開始日に基づき、その勤怠日に有効な時給ルールから算出すること。
- 対象月内に有効な出勤日時があり退勤日時が未登録の勤怠は、不完全勤怠件数に含め、それ以外の不完全勤怠件数と区別して集計すること。退勤未記録だけを根拠に現在も勤務中と断定しないこと。
- 退勤未記録、その他の不完全勤怠、または時給未設定の勤怠がある利用者は、給与一覧で算定上の不足があることを判別できること。個別の原因は給与詳細で確認できること。
- 給与一覧は給与見込みの高い順に表示し、同額の場合はユーザー ID の昇順にすること。表示名や状態を並び順の条件にしないこと。
- 給与一覧では利用者単位で利用者名、給与見込み、算定上の不足の有無を確認できること。
- 給与一覧から対象利用者の給与詳細を開き、スタッフ名、対象月、給与見込み合計、勤怠ごとの勤務日・勤務区分・勤務時間・適用時給・算出金額を確認できること。同日の複数勤怠は勤怠単位で区別すること。
- 給与詳細の各勤怠から対応する勤怠詳細を直接開けること。勤怠詳細では、その勤怠に適用される時給と給与見込み、または算出できない理由を確認でき、給与詳細と同じ計算結果を示すこと。取消済み勤怠は給与集計の対象外として区別すること。
- 給与詳細では、時給未設定、退勤未記録、その他の不完全勤怠を算出済み金額と区別し、未算出の勤怠を合計金額へ含めないこと。退勤未記録を勤務中と断定しないこと。
- 給与詳細では、勤怠ごとの表示額と月次合計の丸め差がある場合に、その差額を確認できること。
- 給与詳細は URL の対象利用者・対象月、認証状態、対象利用者不在、取得失敗を区別して扱うこと。
- データ 0 件、読み込み中、取得失敗を通常の集計結果と区別できること。

## 6. 業務ルール・不変条件

### 6.1 時刻・勤務区分

- 勤怠上の日付・月の判定は日本時間（Asia/Tokyo）を基準に扱う。
- Staff の通常打刻では日付を入力せず、入力時刻を操作時点の JST 日付へ結び付ける。
- 前日から継続する勤務の通常退勤では、操作当日の実際の退勤時刻を使う。
- 日付変更や状態矛盾から前日の退勤日時等を推測しない。
- すべての有効な勤怠は既知の出勤日時を持ち、その出勤日時の日本時間の日付を勤務日とする。
- 勤務中勤怠は既知の出勤日時を持ち退勤日時が未登録の状態、完了済み勤怠は既知の出勤日時と既知の退勤日時を持つ状態として表現する。
- 正しい出退勤日時が確認できない場合は、現在時刻、操作日、退勤日、勤務区分、シフト等から日時を推測して保存しない。
- 月次所属、曜日・祝日判定、時給判定は出勤日時から確定した勤務日を基準にする。退勤が翌日以降になっても退勤日の月へ移動しない。
- 日付変更だけを理由に勤務中勤怠を自動終了・自動補正しない。
- 勤怠の記録精度は分単位を基本とする。
- 勤務区分は昼と夜を区別する。
- 出勤・退勤の順序など成立しない時系列の勤怠を正常完了として扱わない。

### 6.2 勤怠の一貫性

- 1 つの勤怠は 1 回の連続した勤務実績を表し、安定した識別子を付与する。
- 同一利用者・同一勤務日・同一勤務区分でも複数の勤怠を保持でき、件数に上限を設けない。
- 勤務日と勤務区分の一致を勤怠の一意性条件としない。
- 勤怠の対象利用者は作成時に確定し、後から別の利用者へ変更しない。
- 訂正・取消後も変更前の事実、変更経緯、変更実行者を追跡可能にする。
- 同じ勤怠に対する競合更新で、古い状態から新しい状態を上書きしない。
- 同一利用者に勤務中の勤怠を複数共存させない。
- 同一利用者の比較可能な確定勤務時間帯同士が重複する状態を保存しない。ある勤怠の退勤時刻と次の勤怠の出勤時刻が同一である場合は重複とみなさない。
- 勤務時間帯の重複は保存済みまたは保存しようとする既知の実時刻に基づいて判定する。勤務中勤怠の未登録退勤を架空の値へ置き換えず、退勤日時の補記・出退勤日時の訂正では確認済みの実時刻に基づいて保存前に重複を検証する。
- 通常の勤怠操作によって、勤怠の変更履歴を削除しない。

### 6.3 時給・給与

- 時給として扱う値は 0 円以上 99,999 円以下の整数とする。
- 時給は利用者、勤務区分、曜日/祝日、適用開始日により決定する。
- 勤務日が祝日の場合は、通常の曜日ではなく祝日のルールを優先する。
- 適用開始日以前の勤怠へ未来の時給を適用しない。
- 適用候補が複数ある場合、勤怠日に対して有効な最新ルールを用いる。
- 月次の給与見込みも、各勤怠日に対して有効な時給ルールを用いて算出する。
- 既存の時給ルールを編集・削除した場合は、変更後のルール集合に基づいて対象勤怠日の給与見込みが変動し得る。
- 時給ルールの編集前の値や削除済みルールを、操作履歴・監査履歴として保持することは要求しない。
- 勤務時間を算出できない不完全勤怠は給与へ加算せず、不完全勤怠件数として区別する。
- 勤務時間を算出できても時給を決定できない勤怠は給与へ加算せず、時給未設定件数として区別する。
- 給与は勤務分数と適用時給から計算し、月次で集約した後に円単位へ丸める。

### 6.4 管理操作の認可

- 管理者はスタッフと自分自身の勤怠・時給を変更できるが、他の管理者のものは閲覧のみとする。
- 変更可否は対象利用者の操作時点のロールと、操作者本人であるかに基づいて判定する。スタッフから管理者へ変わった利用者の過去データも、他の管理者からは変更できない。
- 対象利用者または変更権限を確認できない場合は変更を許可しない。画面を迂回した禁止操作もサーバー側で拒否し、閲覧可能な既存データは保持する。

## 7. データ要件

システムは、業務上必要なデータを永続的に保持し、少なくとも次の情報を扱えること。

- ユーザーと利用状態
- 認証セッション
- 勤怠の変更履歴と変更実行者
- 時給履歴

関連データは一貫した識別子で参照できること。勤怠の変更履歴は順序を一意に識別でき、通常の勤怠操作によって削除されないこと。月次締めと Event Store の Archive / retention / Compaction は別の責務として扱い、現行機能には含めないこと。データ構造の変更履歴を追跡可能であること。

## 8. 外部インターフェース要件

### 8.1 LINE Platform

staff/admin の本人確認に LINE Login / LIFF から得られる認証情報を利用する。認証結果はサーバー側で検証し、クライアント側の自己申告だけを信用しない。

本システムへの通常アクセスは、運用者が案内する LIFF URL を直接開く方式とし、LINE 公式アカウント、Messaging API、リッチメニュー経由の導線を前提としない。

LINE の認証情報が無効な場合と、LINE Platform 自体を利用できない外部サービス障害は区別して扱えること。

### 8.2 Web 通信・エラー契約

staff/admin の Web UI から server へ行う通信は安全な通信経路を利用すること。入力不正、認証・認可エラー、業務競合、外部サービス障害、内部障害を、利用者向け表示やクライアント処理で必要に応じて区別できること。内部業務処理のための汎用 Web API を設けること自体は要求しない。

## 9. 非機能要件

### セキュリティ

- 管理者専用操作はクライアントの表示制御だけに依存せず、サーバー側でも権限を保証すること。
- 状態変更要求が第三者によって利用者の意図なく実行されないこと。
- 許可していない外部起点からの不正な操作を防止すること。
- secret、接続情報、外部サービスの機密情報をリポジトリへ保存しないこと。

### 信頼性・整合性

- データ構造とアプリケーションの不整合を安全に防止・検出できること。

### ユーザビリティ

- 主要な staff/admin 操作はモバイルファーストとし、スマートフォンで横スクロールを通常閲覧の前提にしないこと。
- PC 専用の別情報構造を持たず、スマートフォンと同じ業務フローを利用すること。

### 運用・監視

- システムの生存状態と依存サービスを含む利用可能状態を区別して確認できること。
- 個々のリクエストや処理を障害調査時に追跡できること。
- 予期しないアプリケーション例外を運用者が把握できること。
- 運用・監視情報へ不要な認証情報・個人情報を含めないこと。

### 保守性

- 変更の影響範囲を責務単位で限定できること。
- クライアントとサーバー間の入出力契約の不整合を防止・検出できること。
- 利用経路によらず主要な業務ルールが一貫して適用されること。
