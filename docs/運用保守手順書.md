# 運用保守手順書

<!-- cspell:ignore YYYYMMDDTHHMMSSZ mktemp dbname -->

## 1. 文書の役割

本書は、本システム稼働後の定常確認、障害切り分け、データ保全、保守作業を定義する。

環境構築・リリース方法は [環境構築・デプロイ手順書](./環境構築・デプロイ手順書.md) を参照する。

> [!NOTE]
> 本書はスナップショット元の実運用リポジトリにおける運用・障害対応・バックアップ・復旧の設計を示す資料です。公開用リポジトリから Production 環境へ接続したり運用操作を実行したりすることは想定していません。実運用向け GitHub Actions は `.github/workflows-disabled` に参考資料として残し、Production の credential や実データは公開用リポジトリに含めません。

## 2. 運用方針

- 利用者データを直接 DB で修正することを通常運用にしない。
- 未登録勤怠の新規作成、勤怠の訂正・取消は、原則として提供されている UI から行う。
- Local、Preview、Production のデータと secret を相互に分離し、別環境の接続先や secret を流用しない。
- 障害時は、利用者画面 → `apps/web` の Vercel deployment / runtime → server log / Sentry → DB の順に影響範囲を絞る。
- 原因が不明な状態で migration のやり直しやデータ削除を行わない。
- secret、LINE token、DB 接続文字列をログ・Issue・文書へ貼り付けない。

## 3. 定常確認

### Vercel

`apps/web` の単一 deployment 状態を確認する。

- 対象 commit が意図した環境へデプロイされているか。
- Build / Deployment が失敗していないか。
- migration gate の失敗有無を確認する。

### Sentry

予期しない例外は Sentry を確認する。主に発生時刻、対象 app、release / environment、stack trace、同一例外の発生頻度を確認する。

障害調査のために不要な個人情報や認証情報を送るよう Sentry 設定を緩めない。

### Server log

Vercel の runtime log で、対象時刻と該当する server 処理の出力を確認する。

Server Action 等の予期しない server 処理失敗は Sentry の operation 情報とあわせて確認する。認証 token、request body 全体、任意の例外内容を安易にログ・監視へ追加しない。

## 4. 利用者からの問い合わせ対応

### ログインできない

1. 通常の staff 入口と `/admin` のどちらで発生しているか確認する。
2. LINE / LIFF のログイン自体が成立しているか確認する。
3. `apps/web` の Vercel deployment / runtime 状態を確認する。
4. server log / Sentry で認証周辺の失敗を確認する。
5. 対象ユーザーが inactive になっていないか確認する。

LINE Platform 側の障害が疑われる場合は、無効な認証情報による利用者側の認証失敗と、LINE Platform 自体を利用できない外部サービス障害を区別する。外部サービス障害時に本システム側の設定変更やデータ修正を先に行わない。

### 打刻できない

1. 現在の勤怠状態を確認する。
2. 未勤務・勤務中・完了済み等の現在状態を確認する。
3. 画面に表示されたエラーを確認する。
4. Sentry と server 側の監視情報で該当する処理の失敗を確認する。
5. 業務上の競合拒否と内部障害を区別する。

出勤・退勤をともに打刻し忘れて勤怠自体が存在しない場合は、実際の出勤日時と退勤日時を確認できるときに限り、管理者の勤怠画面から未登録勤怠を新規作成する。正確な実績日時を確認できない場合に推測時刻で新規作成しない。

未勤務から退勤、勤務中から新規出勤は Staff Recovery へ進まず、通常の状態エラーになる。当日中の打刻忘れで現在状態と矛盾しない場合は、正しい当日時刻を指定した通常打刻で対応する。前日以前の打刻忘れや登録済み勤怠の修正は Admin が対応する。日時を推測して補完しない。前日から実際に継続している勤務は Staff の通常退勤で終了できる。

### 訂正・取消できない

- 操作者の role / status
- 対象勤怠の所有者
- 対象期間や権限制約
- 画面が持つ状態が最新か

を確認する。

### 管理画面が表示できない

1. `/admin` を開いていることと、admin 自身が利用可能な状態であることを確認する。
2. session 失効なら再ログインする。
3. Server Component / Server Action の認証・管理処理でエラーが発生していないか切り分ける。
4. `apps/web` の Vercel deployment / runtime 状態、server log、Sentry を確認する。

## 5. DB 障害・データ整合性

### DB 接続障害

専用の DB 疎通 endpoint は使用せず、次の確認項目から DB 接続を切り分ける。

確認項目:

- Neon 側の稼働状態
- 対象 Vercel 環境の DB 接続設定
- 接続先環境が正しいか
- 直前の migration / deployment の有無

### migration 障害

1. 失敗した migration と対象環境を確認する。
2. 手動再適用の前に DB 状態を確認する。
3. advisory lock の競合か migration 自体の失敗かを切り分ける。
4. schema と migration history の整合を確認する。
5. 必要なら修正 migration を新規作成する。

適用済み migration の履歴を書き換えて帳尻を合わせない。

migration はアプリ切替と原子的に成立するとは限らない。migration が成功した後に Web build または deployment が失敗した場合、DB schema は新しい状態のままでも、public alias は旧 application deployment を指し続けることがある。build / deployment failure を DB rollback 済みとみなさない。

Application rollback は application revision / public alias を戻す操作であり、適用済み migration、DB schema、保存済み Event を自動的には戻さない。rollback 前に、戻す revision が現在 schema と Event Store に存在する Event type / payload format を安全に扱えることを確認する。

新しい Event を旧 reader が解釈できない、旧 revision が現在 schema を扱えない、または後方互換性を確認できない場合は rollback を強行せず、修正版を標準の Production release 経路で roll forward する。

### 勤怠データ

勤怠は event history から現在状態を再構成する。問題がある場合は対象勤怠の event history と version を確認し、イベント内容と変更実行者から誰が操作したかを確認する。

通常の勤怠操作によって Event Stream を削除しない。月次締め・締め解除と Event Store の Archive / retention / Compaction は別の責務であり、現行の通常運用には含めない。データ量削減を目的として個別勤怠の event history を手動削除しない。

未登録勤怠の新規作成や登録済み勤怠の訂正・取消は SQL 直書きで行わず管理画面の提供機能を使用し、Staff 画面では登録済み勤怠を訂正・取消しない。

Current State Projection は Event Store から再構築可能な派生データとして扱う。Projection の欠損・不整合が疑われる場合も Event Store の履歴を直接削除・修正して Projection に合わせず、Event Store を基準に切り分ける。Projection の再構築が必要な場合は「環境構築・デプロイ手順書」の Current State Projection rebuild 手順を使用し、Projection table を手作業の SQL で部分修正して帳尻を合わせない。rebuild が失敗して readiness が未準備のままの場合は、原因を解消するまで ready を手動で書き換えない。

## 6. ユーザー管理

staff の利用停止は管理画面から inactive にする。退職等でも DB row を直接削除するのではなく status 管理を基本とする。

role の変更は通常の管理画面では提供しない。admin の追加・昇格・降格が必要な場合は、通常の staff status 操作とは分離したシステム運用者による管理作業として扱う。

admin の利用状態変更も通常の staff status 操作とは別の管理判断として扱う。

### Production 初回管理者の bootstrap

Production に active admin がまだ存在しない初回利用時だけ、`@repo/server` の `admin:bootstrap:production` を使用して、本人確認済みの LINE identity に対応する `staff / pending` ユーザーを最初の `admin / active` へ変更する。

このコマンドは初期 admin を用意するための one-shot の保守操作であり、通常の role 管理機能ではない。既に別の active admin が存在する状態で新しい admin を追加する用途や、admin の昇格・降格を日常運用する用途には使用しない。

#### 事前確認

1. 対象が Production の Vercel / LIFF / LINE channel / Neon DB であることを確認する。
2. 初期 admin にする本人が Production LIFF から一度ログインする。未登録ユーザーは `staff / pending` として作成されるため、この時点では通常利用できない。
3. bootstrap 対象本人の LINE user ID を、本人の Production LINE identity として確認した値で特定する。display name だけを根拠に対象を決めない。
4. Production の DB host と database name を Neon / Vercel の現在設定から確認する。
5. Production の `DATABASE_URL`、LINE user ID 等の実値を文書、Issue、チャット、共有ログへ貼り付けない。必要な値は利用している secret 管理方法で作業環境へ渡す。

以下では、作業環境に次の値が安全に用意されているものとする。

- `PRODUCTION_DATABASE_URL`: Production の DB 接続文字列
- `PRODUCTION_DATABASE_HOST`: 確認済みの Production DB host
- `PRODUCTION_DATABASE_NAME`: 確認済みの Production database name
- `BOOTSTRAP_LINE_USER_ID`: 本人確認済みの対象 LINE user ID

#### dry-run

最初は `--apply` を付けずに実行する。

```sh
DATABASE_ENVIRONMENT=production \
DATABASE_URL="$PRODUCTION_DATABASE_URL" \
pnpm --filter @repo/server admin:bootstrap:production -- \
  --expected-host "$PRODUCTION_DATABASE_HOST" \
  --expected-database "$PRODUCTION_DATABASE_NAME" \
  --line-user-id "$BOOTSTRAP_LINE_USER_ID"
```

dry-run は DB を更新しない。出力された JSON について、少なくとも次を確認する。

- `mode` が `dry-run`
- `database.host` / `database.database` が確認済みの Production 接続先と一致する
- `targetCount` が `1`
- `target.userId` が今回確認対象として扱う内部 user ID
- `target.role` が `staff`
- `target.status` が `pending`
- `activeAdminCount` が `0`
- `action` が `update`
- `canApply` が `true`
- `reason` が `eligible`

`target` に含まれる `lineUserIdFingerprint` は LINE user ID の完全値ではない。結果を記録する必要がある場合も、DB 接続文字列や LINE user ID の完全値を残さない。

接続先不一致、対象 0 件、複数件、想定外の role / status、既存 active admin 等によって `blocked` になった場合や、上記の期待値と一致しない場合は `--apply` へ進まない。値を推測して guard を回避せず、Production 設定、本人確認済み LINE identity、対象 user の状態を切り分ける。

#### apply

dry-run の確認結果がすべて期待どおりの場合だけ、同じ引数へ `--apply` を追加して実行する。

```sh
DATABASE_ENVIRONMENT=production \
DATABASE_URL="$PRODUCTION_DATABASE_URL" \
pnpm --filter @repo/server admin:bootstrap:production -- \
  --expected-host "$PRODUCTION_DATABASE_HOST" \
  --expected-database "$PRODUCTION_DATABASE_NAME" \
  --line-user-id "$BOOTSTRAP_LINE_USER_ID" \
  --apply
```

成功時は出力 JSON の `mode` が `apply`、`action` が `update`、対象の `role` / `status` が `admin` / `active` になっていることを確認する。

同じ本人に対して誤って再実行した場合は `target-already-admin` の `no-op` となり、別ユーザーを昇格しない。別の active admin が既に存在する状態で `staff / pending` を指定した場合は初期 bootstrap の条件を満たさないため、更新せず停止する。

#### Production での利用確認

1. apply 後、初期 admin 本人が Production LIFF から改めてログインする。
2. `/admin` を開き、管理画面を利用できることを確認する。
3. 「ユーザー」タブから staff の承認・利用停止等、既存の管理機能へアクセスできることを確認する。
4. 確認に失敗した場合は、追加の role / status 変更を手作業で行わず、「管理画面が表示できない」の切り分け手順へ進む。

bootstrap 完了後も、恒久的な role 変更 UI / API は提供しない。通常の staff 管理は既存の管理画面を使用し、初期 admin の bootstrap と日常のユーザー管理を分離する。

## 7. 時給・給与

- 登録済みの時給ルールは管理画面から訂正・削除できる。変更後のルール集合に基づいて過去の給与見込みも変わり得るため、対象利用者、勤務区分、曜日または祝日、適用開始日を確認してから操作する。編集前の値や削除済みルールは監査履歴として保持されない。
- 同一条件・同一適用開始日の重複登録は避ける。
- 不完全勤怠や時給不足がある場合、給与値だけで締め判断しない。
- 給与見込みは各勤怠日に有効な時給ルールから算出し、未来の適用開始日の時給を過去勤怠へ適用しない。
- 月次締め・締め解除は現行機能に含まれないため、給与一覧・給与詳細に表示される給与見込みを業務上の締め状態として扱わない。

## 8. バックアップ・復旧

### 復旧手段と保持範囲

Production DB は Neon の短期履歴と Cloudflare R2 の日次論理バックアップを役割分担して使用する。

Neon の history retention は plan や project 設定によって変わるため、障害対応時に現在の保持期間を確認する。必要な復旧時点がその保持期間内で Neon を利用できる場合は、必要な復旧時点から一時 branch を作成して内容を確認するなど、Neon の point-in-time recovery を第一候補にする。保持期間を固定値として運用判断に埋め込まず、現在の設定を基準に判断する。

R2 backup は GitHub Actions の `Production DB Backup Scheduler` が毎日 03:17（Asia/Tokyo）に `main` を ref として `Production DB Backup` を起動し、必要に応じて本体 workflow を手動実行できる。scheduler は default branch 上で動作し、checkout せず、Production DB / R2 credential や `production` Environment を参照しない。実際の backup job は `main` の workflow revision だけで実行し、`production` Environment の credential を使用する。Environment の deployment branches/tags は `main` のみに制限する。scheduled backup だけを使用する場合の復旧地点は原則として最大約 24 時間間隔であり、Neon の point-in-time recovery の代替ではない。R2 の `production/` prefix は Object Lifecycle Rule で 30 日後に expire するため、30 日を超える長期保管は保証しない。

R2 には PostgreSQL 18 の custom-format dump と対応する SHA-256 checksum を保存する。workflow 内では upload 前に `pg_restore --list` が成功すること、upload 後に remote ContentLength と local dump size が一致することを確認する。ただし、workflow 成功だけでは実際の restore 成功を保証したことにはしない。

### Application rollback / roll forward / restore / Projection rebuild の判断

Production 障害では application revision、DB schema、Event Store 等の原本データ、Current State Projection を別の状態として切り分ける。Application deployment を戻すことを、DB や Event data を戻すことと同一視しない。

| 状況                                                                                                              | 選択する手段         | 判断上の注意                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------ |
| 新 application revision に問題があるが、以前の revision が現在の DB schema と保存済み Event format を安全に扱える | Application rollback | public Production alias を以前の検証済み deployment へ戻しても、schema / Event data は現在状態のまま残る     |
| migration や Event format が前進し、以前の revision との後方互換性がない、または互換性を確認できない              | Roll forward         | rollback を強行せず、修正版を `main` の Quality → `deploy-production` 経路で反映する                         |
| Event Store その他の原本データが破損・欠損し、正常な原本からの再生成だけでは復旧できない                          | DB restore           | 復旧地点より後の更新を失う可能性があるため、既存の backup / restore 手順で内容を非本番確認してから切り替える |
| Event Store は正常だが Current State Projection だけが欠損・不整合・not-ready                                     | Projection rebuild   | Event Store を Source of Truth として既存 rebuild 手順を使い、DB restore や Event Store の手修正を行わない   |

判断順序は次のとおりとする。

1. Event Store 等の原本データが正常か確認する。原本データ自体が破損・欠損している場合は restore を検討する。
2. 原本データが正常で Projection だけが不整合なら Projection rebuild を使用する。
3. application release の問題なら、rollback 候補 revision と現在の schema / Event format の後方互換性を確認する。
4. 後方互換性を確認できる場合だけ Application rollback を候補にする。
5. 新しい Event を旧 reader が読めない場合、旧 revision が現在 schema を扱えない場合、または互換性が不明な場合は roll forward を選ぶ。
6. 復旧後は GitHub Actions の対象 SHA、Vercel deployment、public Production alias の対応を再確認し、必要な staff / `/admin` 操作を確認する。

Application rollback を行う場合は、戻す deployment が過去に検証済みであることと、現在の Production public alias がその deployment を指したことを Vercel 側で確認する。単に過去の deployment が `READY` であるだけでは rollback 完了とみなさない。

### 定常確認

- GitHub Actions の `Production DB Backup Scheduler` の直近 scheduled run と、その run が `main` へ dispatch した `Production DB Backup` の実行結果を確認し、実際の backup job が成功していることを確認する。
- R2 に最新の `.dump` と対応する `.dump.sha256` が両方存在することを確認する。
- workflow log、Issue、文書へ DB 接続文字列や R2 credential が出力されていないことを確認する。
- backup pipeline、PostgreSQL major version、R2 credential、restore 手順を変更した場合は、Production DB を直接変更せず非本番環境への restore を再検証する。

### 復旧地点の選択

1. 障害が発生した時刻と、データが正常だった最後の時刻を特定する。
2. Neon の現在の history retention を確認し、必要な復旧時点が保持期間内で Neon を利用できる場合は point-in-time recovery を優先して、まず一時 branch で内容を検証する。
3. 必要な復旧時点が Neon の保持期間外である場合、Neon とは独立した copy が必要な場合、または Neon の短期復旧を利用できない場合は R2 を使用する。
4. R2 では障害発生より前の最新 `.dump` を選ぶ。手動 backup が存在する場合も timestamp を確認して復旧地点を決める。
5. 検証目的で Production DB に `pg_restore` を実行しない。必ず一時的な非本番 DB へ restore する。

### R2 backup の download と検証

R2 credential、Account ID、bucket 名は安全な secret 管理から現在の shell へ設定し、実値を command history や文書へ残さない。復旧対象 object key だけを `BACKUP_KEY` に指定する。

```sh
export AWS_REGION=auto
export AWS_DEFAULT_REGION=auto
export R2_ENDPOINT="https://${R2_BACKUP_ACCOUNT_ID}.r2.cloudflarestorage.com"
export BACKUP_KEY='production/YYYY/MM/DD/timecard-YYYYMMDDTHHMMSSZ.dump'

RESTORE_DIR="$(mktemp -d)"
DUMP_NAME="$(basename "${BACKUP_KEY}")"

aws s3 cp \
  "s3://${R2_BACKUP_BUCKET}/${BACKUP_KEY}" \
  "${RESTORE_DIR}/${DUMP_NAME}" \
  --endpoint-url "${R2_ENDPOINT}"

aws s3 cp \
  "s3://${R2_BACKUP_BUCKET}/${BACKUP_KEY}.sha256" \
  "${RESTORE_DIR}/${DUMP_NAME}.sha256" \
  --endpoint-url "${R2_ENDPOINT}"

(
  cd "${RESTORE_DIR}"
  sha256sum -c "${DUMP_NAME}.sha256"
)

docker run --rm \
  --volume "${RESTORE_DIR}:/backup:ro" \
  postgres:18-bookworm \
  pg_restore --list "/backup/${DUMP_NAME}" \
  > /dev/null
```

checksum 不一致、download 失敗、`pg_restore --list` 失敗のいずれかが発生した backup は restore 元として使用しない。別の backup point を選ぶ前に、対象 object と workflow run の状態を確認する。

### 非本番 DB への restore

Production と共有 Preview / Local を restore test に使用しない。Neon で Production から一時 branch を作成し、その一時 branch 上に restore 専用の空 database `timecard_restore_check` を作成する。

一時 branch の owner 接続で次を実行する。

```sql
CREATE DATABASE timecard_restore_check;
```

`timecard_restore_check` への direct connection string を取得し、`sslmode=verify-full` を使用して `RESTORE_DATABASE_URL` として現在の shell に設定する。実値は repository、Issue、文書へ記録しない。

restore 前に接続先 database を確認し、`timecard_restore_check` 以外を指している場合は停止する。

```sh
docker run --rm \
  --env DATABASE_URL="${RESTORE_DATABASE_URL}" \
  postgres:18-bookworm \
  sh -c 'psql "$DATABASE_URL" -Atc "select current_database()"'
```

出力が `timecard_restore_check` であることを確認してから restore する。

```sh
docker run --rm \
  --env DATABASE_URL="${RESTORE_DATABASE_URL}" \
  --env DUMP_NAME="${DUMP_NAME}" \
  --volume "${RESTORE_DIR}:/backup:ro" \
  postgres:18-bookworm \
  sh -c 'pg_restore --dbname="$DATABASE_URL" --no-owner --no-acl --exit-on-error "/backup/$DUMP_NAME"'
```

restore error を無視したり、Production DB に対して再試行したりしない。dump 内容や migration history を手作業で書き換えて restore を通さない。

### restore 後のデータ検証

restore 先で current schema の主要 table と Drizzle migration history を確認する。確認結果に個人情報を含む row 本文を Issue やログへ転記しない。

```sh
docker run --rm -i \
  --env DATABASE_URL="${RESTORE_DATABASE_URL}" \
  postgres:18-bookworm \
  sh -c 'psql "$DATABASE_URL" -v ON_ERROR_STOP=1' <<'SQL'
select table_schema, table_name
from information_schema.tables
where table_schema in ('public', 'drizzle')
  and table_type = 'BASE TABLE'
order by table_schema, table_name;

select
  (select count(*) from users) as users,
  (select count(*) from attendance_events) as attendance_events,
  (select count(*) from attendance_current_states) as attendance_current_states,
  (select count(*) from hourly_wage_rates) as hourly_wage_rates;

select role, status, count(*)
from users
group by role, status
order by role, status;

select count(*) as attendance_event_count,
       min(created_at) as oldest_event_at,
       max(created_at) as newest_event_at
from attendance_events;

select count(*) as hourly_wage_rate_count,
       min(effective_from) as oldest_effective_from,
       max(effective_from) as newest_effective_from
from hourly_wage_rates;

select id, hash, created_at
from drizzle.__drizzle_migrations
order by id;
SQL
```

主要 table が存在し、query が成功することを確認する。Production に代表データが存在する場合は、user role / status の集計、attendance event の件数と時刻範囲、hourly wage rate の件数と適用日範囲が復旧地点として不自然でないことを確認する。個別の LINE user ID、event payload、時給の個別値等を確認記録として外部へ貼り付けない。

Current State Projection は Event Store から再構築可能な派生データだが、restore test では dump に含まれた `attendance_current_states` も正常に読み取れることを確認する。Projection の不整合が疑われる場合は Event Store を書き換えず、既存の Projection rebuild 手順を別途使用する。

### migration と application revision の整合確認

backup object key の UTC timestamp から、その時点で active だった Vercel Production deployment と対応する `main` の exact Git SHA を特定する。

restore した `drizzle.__drizzle_migrations.created_at` の並びを、候補 revision の `packages/db/migrations/meta/_journal.json` にある `when` と照合する。restore DB に candidate revision が知らない migration が含まれている場合、その revision を接続しない。backup 時点の application revision をそのまま使用する場合は、restore DB の最新 `created_at` と candidate revision の最新 migration `when` が一致することを確認する。

migration history を直接 INSERT / UPDATE / DELETE して application version に合わせない。

schema の migration history が整合していても、それだけで古い application revision へ rollback できるとは限らない。Event Store に、rollback 候補 revision が知らない Event type や解釈できない payload format が保存されている場合、その revision を Production へ戻さない。schema と Event format の両方について後方互換性を確認する。

現在の application revision の方が新しく、restore DB を新しい schema へ進める必要がある場合は、restore test 中に ad hoc migration を実行しない。復旧地点の内容を確認した後、Production の標準 `main` release による migration → deployment の経路で前進させるか、backup 時点の application revision と組み合わせて復旧するかを判断する。

### 実障害時の Production 復旧

最初に「Application rollback / roll forward / restore / Projection rebuild の判断」に従って障害の対象を切り分ける。原本データが正常で Application rollback、roll forward、または Projection rebuild だけで復旧できる場合は DB restore を行わない。

DB restore が必要と判断した場合は、非本番 restore とデータ・migration・application revision・Event format の整合確認が完了するまで Production 接続先を変更しない。

R2 backup を使用する場合は、backup timestamp より後から障害発生までの更新が失われる可能性を明確にする。切替作業中に旧 Production への新規書き込みが継続してデータが分岐しないよう、必要に応じて application 側の書き込みを停止してから復旧先へ切り替える。

復旧先を application へ接続した後は、staff の主要な読み取り、`/admin` の主要な読み取りを確認する。migration や Projection rebuild が必要な場合は、それぞれ既存の正式な運用手順を使用する。

restore test 用の一時 Neon branch は検証結果を確認した後に削除する。Production DB、共有 Preview DB、通常の Local DB を restore test の後片付け対象として削除しない。

## 9. セキュリティインシデント対応

secret、認証情報、個人情報の漏えい、不正なセッション利用、権限外の操作等が疑われる場合は、通常の機能障害と区別して影響拡大の防止を優先する。

### 初動

1. 発生時刻、対象環境、対象サービス、疑われる情報・操作の範囲を特定する。
2. secret や個人情報の実値を Issue、チャット、共有ログへ転記せず、GitHub Actions run、Vercel deployment、Sentry event 等の参照可能な識別情報だけを記録する。
3. 漏えいまたは不正利用が疑われる credential は、影響範囲を確認したうえで失効・rotate し、旧 credential が利用できないことを確認する。
4. セッションの不正利用が疑われる場合は、影響を受ける既存セッションを失効させ、必要に応じて対象スタッフを利用停止にする。
5. データの不正変更や欠損が疑われる場合は、直接 SQL で帳尻を合わせず、変更履歴・監視・DB 状態を確認して [バックアップ・復旧](#8-バックアップ復旧) の判断へ進む。

### 影響範囲の確認

事故の種類に応じて、少なくとも次の境界を確認する。

- GitHub repository / Actions の Secret・Variable と workflow log
- Vercel の environment variable、deployment、runtime log
- Neon の DB credential、role、接続履歴と対象データ
- LINE Login / LIFF の credential と認証経路
- Sentry に送信された event / breadcrumb
- Cloudflare R2 の backup credential と object
- 本システムの認証セッション、利用者状態、勤怠変更履歴

無関係な credential まで一律に変更するのではなく、漏えい経路と共有範囲を確認して必要な範囲を封じる。反対に、同じ credential を複数環境や複数用途で共有していたことが判明した場合は、その共有先も影響範囲に含める。

### 復旧後

1. credential、session、deployment、DB 等の復旧後状態を確認し、主要な staff / admin 操作が成立することを確認する。
2. 不正なデータ変更があった場合は、Event Store、migration history、backup 等の Source of Truth を基準に整合性を確認する。
3. 原因となった設定、権限、ログ出力、運用手順を修正し、同じ漏えい経路を残さない。
4. 長期的な設計変更が必要な場合は、通常の Issue / docs / ADR の管理へ戻して追跡する。
