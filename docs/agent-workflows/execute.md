# AI エージェントによる実行

確定済みの実装計画を本リポジトリへ反映するためのワークフローを定義する。

このワークフローは、受け取った計画を実行することを担当する。計画の具体性の判定、妥当性確認、再計画、タスク分割、タスク境界の再設計を既定動作にしない。

## 入力

実行可能な粒度まで確定した実装計画を入力として受け取る。

実行中に、計画だけでは決められない重要な仕様や対象範囲が新たに必要になった場合は、親エージェントが独自に再計画して続行せず、不足している判断を報告して停止する。

## 役割分担

ファイル変更を伴うタスクは、サブエージェントを利用できる環境では階層型のマルチエージェントで実行する。

親エージェントは **オーケストレーションとエスカレーションされた判断**を担当する。タスクの進行管理、サブエージェントの起動・再利用、Git 状態や SHA の確認、レビュー結果に応じた repair の振り分け、次の段階へ進むかの判断を行う。通常の実装、通常の Task review、実行全体レビュー、validation failure の通常調査を自ら代行しない。原則として親エージェント自身はファイルを編集・commit しない。

実装サブエージェントは、担当タスクに必要な局所的な調査、実装、関連するテストや文書の更新、必要な検証、commit 作成までを担当する。

レビューサブエージェントは実装担当とは分離し、担当範囲の要求、diff、検証結果を独立に確認して PASS / BLOCKING を判定する。十分な根拠をもって安全に判定できない場合だけ親エージェントへエスカレーションする。親エージェントは通常の PASS 判定を重複レビューしない。

Git 状態や SHA の確認、対象 commit の特定など、ファイル変更や意味的な実装判断を伴わない機械的な作業は親エージェントが直接行ってよい。

サブエージェントを利用できない場合は、親エージェントが黙って実装・通常レビュー・実行全体レビューを代行せず停止して報告する。

### サブエージェントのセッション

ファイル変更を伴う各タスクの実装は、**原則として新しい実装サブエージェント**へ委譲する。前のタスクと関連が強いという理由だけで、同じセッションを継続利用しない。

同じタスクの repair は、そのタスクを担当した実装サブエージェントへ戻す。

後続タスクで前のタスクの実装サブエージェントを再利用するのは、実装計画や実行入力で明示的に指定されている場合だけとする。指定がない場合は新しい実装サブエージェントを使用する。

各タスクのレビューには、実装担当とは別の **新しい Task reviewer** を原則 1 セッション作成する。同じタスクの repair commit を再レビューするときは、その Task reviewer を再利用する。別タスクへ Task reviewer を使い回さない。

すべてのタスクが Task review を通過した後の実行全体レビューには、それまで実装や Task review に使っていない **新しい実行全体 reviewer** を 1 セッション作成する。実行全体レビュー中の repair cycle では同じ reviewer を再利用する。

新しいサブエージェントには、担当範囲、必要な前提 commit、関連ファイル、制約など、その役割の実行に必要な局所的コンテキストだけを渡す。過去タスクの会話ログや不要な調査結果を一括で引き継がず、必要な前提は commit 済みのリポジトリ状態から確認する。

新しい実装サブエージェントへ委譲するときは、確定済み実装計画の担当タスク定義を原則そのまま用い、親エージェントが背景・目的・制約を長文で再作文しない。レビューサブエージェントにも、レビュー対象と判定に必要な要求・commit・検証結果だけを渡す。

## タスクの実行とレビュー

実装計画で定めた順にタスクを実行する。

実装サブエージェントがタスクの commit を作成した後、Task reviewer は担当タスクの定義、対象 commit の差分、実行された検証の結果を確認して、タスクの要求を満たしているか独立にレビューする。実装担当が既に行ったリポジトリ全体の調査を最初から繰り返さず、要求との対応や差分の妥当性に不明点・矛盾がある場合だけ必要な周辺情報を追加確認する。

Task reviewer が BLOCKING と判定し、修正方針を十分な根拠をもって示せる場合は、同じタスクの実装サブエージェントへ repair を戻す。repair 後は同じ Task reviewer が再レビューする。独立した別の関心事を同じ commit に混ぜない。

Task reviewer が要求の解釈、設計判断、影響範囲、検証結果などを自力で安全に判定できない場合は、無理に PASS / BLOCKING を決めず親エージェントへエスカレーションする。親エージェントが既存の確定要求・計画・repository state から解決できる場合は判断を返して同じレビューを継続する。ユーザー判断や再計画が必要な場合は停止して不足を報告する。

Task review を通過した後に次のタスクへ進む。

## 実行全体レビューと標準品質確認

すべての変更タスクが Task review を通過したら、新しい実行全体 reviewer を起動する。

実行全体 reviewer は、確定済み実装計画、Run 開始時の基準 state、現在の HEAD、Run 全体の差分、各タスクの検証結果を必要な範囲で確認し、タスク単体では見落としやすい要求漏れ、タスク間の不整合、不要な変更、tests / docs の不足をレビューする。

明確な BLOCKING finding がある場合は、標準品質確認を先に繰り返さず repair を行う。修正対象が既存タスクへ明確に帰属する場合はその実装サブエージェントへ戻し、既存タスクの局所コンテキストへ自然に帰属しない修正は新しい実装サブエージェントへ委譲する。実行全体 reviewer 自身はファイルを編集・commit しない。

実行全体 reviewer は、意味的な全体レビューで未解決の BLOCKING がなくなった時点で、`CONTRIBUTING.md` で定義されたリポジトリ全体の標準品質確認を自ら実行する。

標準品質確認が失敗した場合も、実行全体 reviewer が失敗内容の切り分けと repair 方針の決定を担当する。修正方針を十分な根拠をもって決められる場合は適切な実装サブエージェントへ repair を委譲し、修正後の差分確認と必要な検証、標準品質確認を同じ実行全体 reviewer が継続して行う。

validation failure では、同じ条件の全件実行を繰り返して偶然の PASS を待たない。同一条件の単純リトライは再現性確認のため原則 1 回までとし、その後は failing test、runtime log、並列度、共有 resource など、より小さい診断で原因仮説を確認する。skip、assertion の無根拠な緩和、待機時間の無根拠な増加、検証対象の runtime 契約を変える workaround だけで green にしない。

実行全体 reviewer が要求の解釈、設計判断、影響範囲、validation failure の原因や修正方針を安全に判断できない場合だけ、親エージェントへエスカレーションする。親エージェントは通常の全体レビューやデバッグを重複して行わず、エスカレーションされた判断に必要な範囲だけ確認する。

実行全体 reviewer が Run 全体に未解決の finding がなく、標準品質確認も PASS したと判定した時点で、実装 workflow の internal PASS とする。

## Database migration の guard 拒否

`packages/db/migrations` に対する hook の拒否を `git add .`、`git add -A`、shell 展開・連結などで回避しない。migration を生成する場合は schema を変更し、`pnpm --filter @repo/db generate -- <migration-name>` を実行する。生成後の stage は対象 migration ファイルを明示して `git add -- <migration-file>` を使う。拒否理由が不明、または guard が操作を判断できない場合は実行を止め、コマンドと拒否内容を報告する。

## 実ブラウザ確認

ユーザーに見える画面変更で実ブラウザ確認が必要な場合は、変更対象の実際の route / page を表示して確認する。確認専用の一時 page / component を作り、対象画面の代替として扱わない。

staff / admin など認証が必要な画面をローカルで自動確認する場合、認証フロー自体が確認対象でない限り、まず既存の Playwright E2E 環境と認証 fixture を再利用して認証済み状態を作る。実 LINE / LIFF 認証は、認証フローそのものの確認や手動 smoke test が目的の場合に使用する。

既存の E2E setup で対象画面を表示できない場合は、代替画面で確認済みとせず、対象タスクを完了としないで理由を報告する。ブラウザ確認のためだけに作成した一時ファイルや生成物を tracked file に残さない。

## AI 利用量

AI エージェントのトークン消費量は、品質・安全性と並ぶ重要な実行最適化対象とする。必要な検証やレビューを省略せず、一連の実装作業で不要なコンテキストを持ち回らないことを優先する。

実行環境から正確なトークン数を取得できる場合は、その実装作業で使用したトークン数を記録する。マルチエージェント全体の消費量を正確に集計できる場合は、親エージェントとサブエージェントを含む一連の実装作業全体の値を使用する。

正確なトークン数を取得できない場合は、推測や利用枠からの換算を行わない。利用枠の残量など別の利用量情報を取得できる場合は、トークン数とは区別した補助指標として記録してよい。

トークン消費を抑えるため、特に次を避ける。

- 後続タスクまで同じ実装サブエージェントや Task reviewer を不要に使い回し、長い会話履歴を持ち続けること
- 同じタスクの repair ごとに新しい reviewer を作り、同じ前提を繰り返し読み直すこと
- 新しいサブエージェントへ過去タスクの会話や一連の実装作業全体の調査結果を必要以上に再投入すること
- 親エージェントがサブエージェントの通常レビューや validation failure 調査を重複してやり直すこと
- 無関係な文書・コードの再読込
- 同じ目的の調査・レビューの重複

利用量が継続的に大きい場合は、サブエージェントの分割、渡すコンテキスト、文書読み込み、重複した調査やレビューを見直し、repository-local なルールや文書構成の改善材料とする。
