# AI エージェントによる計画

本システムの変更要求または粗い実装案から、実行可能な実装計画を作るためのワークフローを定義する。

このワークフローは計画の作成までを担当し、ファイル変更や commit は行わない。

## 入力

要求、Issue、または人が作成した粗い実装案を入力として受け取る。

実装案にタスクの順序や変更単位が示されている場合は、その意図を尊重する。固定の計画テンプレートは要求しない。

## 計画

`AGENTS.md` と `CONTRIBUTING.md`、および変更に関係するコード・テスト・文書を必要な範囲で確認する。

実装担当が追加の大きな設計判断をせず着手できるところまで、変更単位、順序、必要な検証、関連する文書更新を具体化する。

一連の実装作業は原則として 1 つの関心事だけを扱う。一連の実装作業を 1 つの変更として自然に説明できない複数の関心事が含まれる場合は、実行前に実装作業を分ける。

変更単位は原則として独立して説明できる関心事またはその一貫した部分ごとにタスクへ分ける。同じ関心事に属する実装・テスト・文書更新は、層やファイルが異なることだけを理由に別タスクへ分割しない。人が指定した境界が実装上成立する場合は維持する。

ただし、同じ関心事でも 1 つのタスクが大きくなりすぎる場合は、タスク数を減らすことを優先しない。1 つのタスクとして実装・検証・レビューまで完了できる現実的な規模にする。

1 つのタスクに複数の大きな責務変更、広範な依存関係の切替、旧実装の撤去などが重なり、実装・検証・レビューが過大になる場合は、同じ関心事の中でも順序関係が明確な段階へ分割する。その場合は、各タスクが独立して目的を説明でき、変更後の状態が次のタスクの前提として成立し、必要な検証を実行できる境界を選ぶ。層やファイル数だけを理由に機械的に分割しない。

計画を詳細化するためだけに、実装そのものや不要な広範囲の調査を先行して行わない。

## 出力

実行順に並んだ変更タスクと、それぞれの目的、変更内容、必要な検証、タスク境界が分かる実装計画を出力する。

ファイル名や関数名・型名などが実装に必要で、現在のリポジトリから確定できる場合は計画に含めてよい。一方、形式を満たすためだけの情報は追加しない。

このワークフロー単独では、計画を出力した時点で停止する。人が計画をレビュー・修正した後、その計画を `execute.md` へ渡して実行できる。
