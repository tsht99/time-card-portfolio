# 用語集

## 1. 文書の役割

本書は、本システムで使用する業務用語の意味を主要な業務境界ごとに定義する。

会話、Issue、要求・設計文書、UI、コードでは、同じ業務概念を原則として同じ用語で表す。意味が業務境界によって異なる場合は、無理に全体で一つの定義へ統一せず、その境界での意味を明示する。

本書は詳細な業務ルールや実装仕様を複製しない。具体的な振る舞い・制約は [要件定義書](./要件定義書.md)、責務境界・処理方式は [設計書](./設計書.md)、設計判断の背景は [ADR](./adr/) を Source of Truth とする。

## 2. 業務境界

本システムの主要な業務境界は [ADR 0002](./adr/0002-modular-monolith-with-domain-boundaries.md) に従い、次の三つとする。

- Users / Access
- Attendance
- Payroll Estimate / Hourly Wage

本書では、この業務境界を用語の分類にも使用する。一つの概念が複数の境界で利用される場合は、その概念を所有する境界で定義し、他の境界では同じ意味のまま参照する。

## 3. Users / Access

### 利用者

本システムに登録される人。スタッフと管理者を含む。

### スタッフ

`staff` ロールを持つ利用者。

出勤・退勤、自身の勤怠確認など、スタッフ向けの操作を行う。利用可否はスタッフの利用状態によって管理する。

### 管理者

`admin` ロールを持つ利用者。

ユーザー管理、勤怠管理、時給管理、給与見込みの確認など、管理者向けの操作を行う。

### 本人確認

LINE の認証情報によって、アクセスしている人の本人性を確認すること。

本人確認の成功は、本システムの利用許可を意味しない。未承認のスタッフは本人確認に成功しても利用を開始できない。

### 利用状態

スタッフが本システムを利用できる状態を表す区分。

- 承認待ち: `pending`
- 利用中: `active`
- 利用停止: `inactive`

管理者向けのロールと、スタッフの利用状態は別の概念として扱う。

### 承認待ち

LINE による本人確認後、管理者による利用承認を待っているスタッフの状態。

本システム上の利用者としては存在するが、承認されるまで利用を開始できない。

### 利用中

本システムの利用が許可されているスタッフの状態。

### 利用停止

本システムの継続利用を許可しないスタッフの状態。

勤怠の「取消」とは関係がない。利用停止は利用者のアクセス状態を表し、既存の勤怠そのものを無効にはしない。

### 利用承認

承認待ちのスタッフを利用中へ変更し、本システムの利用を許可すること。

### 表示名

システム上で利用者を識別するための業務用名称。

初回登録時には LINE の表示名を初期値として利用できるが、その後は LINE のプロフィール表示名とは独立して扱う。

## 4. Attendance

### 勤怠

一回の勤務について、出勤日時、退勤日時、勤務日、勤務区分などを記録する単位。

同じ利用者・同じ勤務日・同じ勤務区分であっても、別の勤務であれば複数の勤怠が存在できる。

### 出勤

勤務を開始した事実、およびその日時。

### 退勤

勤務を終了した事実、およびその日時。

### 勤務中

出勤が記録されており、退勤がまだ記録されていない勤怠の状態。

退勤日時がないという事実だけから、現在も実際に勤務していると推測する意味では使用しない。

### 完了済み

出勤日時と退勤日時が記録され、勤務時間を確定できる勤怠の状態。

取消済みの勤怠は、有効な完了済み勤怠として扱わない。

### 勤務日

勤怠を日単位で扱うための基準日。

出勤日時の日本時間（Asia/Tokyo）の日付から決定し、独立した入力値として扱わない。

### 勤務区分

一回の勤怠が昼勤務か夜勤務かを表す区分。

Attendance で記録された勤務区分は、Payroll Estimate / Hourly Wage でも適用する時給を選ぶ条件として同じ意味のまま利用する。

### 通常打刻

スタッフが、現在の勤務状態と矛盾しない形で実際の出勤または退勤を記録する操作。

登録済み勤怠を事後に変更する「訂正」や、勤怠を無効にする「取消」とは区別する。

### 未登録勤怠

実際には勤務が行われたが、まだ勤怠記録として登録されていない勤務。

管理者は、確認できた正しい出勤日時と退勤日時に基づいて新規作成する。未確認の日時を推測して補完する意味では使用しない。

### 訂正

登録済み勤怠の内容を、確認できた正しい内容へ変更すること。

勤怠全体を無効にする「取消」とは区別する。訂正前後の変更経緯は勤怠の変更履歴から追跡できる。

### 取消

登録済みの勤怠全体を、有効な勤怠として扱わない状態へ変更する不可逆な操作。

物理削除ではなく、出勤だけ・退勤だけを対象とする部分取消や、取消後の復活も意味しない。

### 変更履歴

勤怠に対して行われた新規作成、訂正、取消などの変更経緯と操作者を追跡するための履歴。

## 5. Payroll Estimate / Hourly Wage

### 時給

勤務時間に対して適用する一時間あたりの金額。

本システムでは、対象利用者、勤務区分、曜日または祝日、適用開始日に基づいて適用する時給を決定する。

### 時給ルール

特定の利用者・勤務区分・日区分について、ある適用開始日以降に使用する時給を定めるルール。

同じ条件について対象日時点で有効な候補が複数ある場合は、対象日以前で最も新しい適用開始日のルールを使用する。

### 日区分

時給ルールを選ぶための曜日または祝日の区分。

勤務日が祝日の場合は、通常の曜日より祝日の区分を優先する。

### 適用開始日

時給ルールが有効になり始める日。

対象の勤怠日に適用するルールを選ぶときの基準として使用する。

### 適用時給

対象となる勤怠の利用者、勤務区分、日区分、勤怠日に基づいて選択された時給。

### 時給未設定

対象となる勤怠日に適用できる時給ルールが存在しない状態。

時給として 0 円が設定されている状態とは区別する。

### 不完全勤怠

給与見込みの算定に必要な勤務時間を確定できない勤怠。

退勤日時が未登録である場合を含むが、不完全勤怠であることだけを根拠に現在も勤務中であると断定しない。

### 給与見込み

本システムに記録された勤務分数と設定済みの時給ルールから算出する月次の見込み額。

税、社会保険、源泉徴収、法定割増、給与明細などを含む一般的な給与計算全般を意味しない。

### 算定上の不足

給与見込みを完全に算定できない原因となる情報不足。

不完全勤怠や時給未設定などを区別して扱う。

### 要確認

給与見込みの対象に算定上の不足があり、管理者による確認が必要であることを示す状態。

個別の不足理由そのものを意味せず、理由は給与詳細で確認する。

### 端数調整

勤怠ごとの表示額と、利用者・月単位で算出して丸めた給与見込み合計との間に生じる丸め差を表す表示上の調整額。

## 6. 用語の運用

- 一般的な技術用語ではなく、本システムの業務上の意味を共有する必要がある用語を対象とする。
- 新しい業務概念を導入するときは、既存の用語で表せないかを先に確認する。
- 同じ言葉が複数の業務境界で異なる意味を持つ場合は、全体で一つの意味へ無理に統一せず、境界ごとの意味を明示する。
- 「状態」のように単独では意味が曖昧な語は、必要に応じて「利用状態」「勤怠状態」のように対象を明示する。
- 用語の意味を変更した場合は、要求・設計・UI・コードの名称との整合性も確認する。
