# テスト方針

## 1. 文書の役割

本書は、本システムのテスト戦略、テストレベル、主要な品質保証の考え方、実行方法を定義する。

要件は [要件定義書](./要件定義書.md)、システム方式と主要設計は [設計書](./設計書.md) を参照する。

個別テストケースの入力・期待結果は本書で二重管理せず、具体的なテスト仕様の Source of Truth はテストコードとする。

## 2. 基本方針

- 不具合を可能な限り内側の低コストなテストで検出する。
- 実 DB や実ブラウザが必要な性質だけを外側のテストへ持ち出す。
- 同じ仕様を複数レベルで機械的に重複検証しない。
- 変更による主要リスクに対応する保証点を明確にする。
- テストコード自体も保守対象とし、実装詳細へ過剰に結合しない。
- 通常の自動テストで使用するアプリケーション設定は、テストコードまたはリポジトリで管理するテスト専用設定から決定的に与え、開発者ローカルの設定へ暗黙依存しない。
- Docker、実ブラウザ等のテストレベル上必要な外部実行環境への依存は、必要なテストレベルと実行方法から確認できる状態にする。

### テスト設計原則

テストケースは、実装手順ではなく、要求・業務ルール・利用者や呼び出し側から観測可能な振る舞い・境界の契約を具体例として表す。テストコードは、これらを継続的に検証する実行可能な仕様例として扱う。ただし、要求の背景、設計意図、運用判断までテストへ重複記載せず、それぞれの文書を Source of Truth とする。

- テスト名は、前提または条件と、保証する振る舞いが分かる名前にする。Issue 番号や過去の変更経緯をテスト名へ残さない。
- 利用者や呼び出し側から観測できる結果を優先して検証する。DOM 構造、CSS class、内部関数の呼び出し回数等は、それ自体が契約でない限り固定しない。
- 一つの仕様には主な保証先となるテストレベルを定め、他レベルで同じケースを網羅的に重複させない。
- 正常系の網羅ではなく、変更時のリスクに応じて境界値、不正な状態遷移、認証・認可、競合、時刻・金額等の重要なケースを選ぶ。組み合わせが多い場合は、状態遷移表や決定表で整理する。
- 広い入力範囲に対する不変条件は、具体例の列挙より Property-based Test が適する場合に利用する。
- 不具合修正では、可能な限り修正前に失敗する回帰テストで不具合を再現し、そのテストを修正後も残す。
- 一つのテストは主に一つの理由で失敗するように保つ。外部仕様を変えないリファクタリングで多数のテスト修正が必要になる場合は、実装詳細への結合を見直す。
- UI では、操作可否、表示状態、アクセシビリティ、画面幅による操作不能や横方向のはみ出し等、利用者に影響する振る舞いを保証する。特定の CSS class、色値、座標、ピクセル値は、明示的なデザイン契約でない限り固定しない。
- 列境界、配置、表示領域の幅などが明示的なデザイン契約である場合は、実ブラウザを使う Medium E2E で bounding box 等から不変条件を数値検証してよい。個別の CSS class や絶対座標ではなく、揃えるべき要素間の相対位置、共通幅、余白の対称性等を保証し、sub-pixel rounding を超えて不要に広い許容差を設けない。
- screenshot と目視確認は、自動化しにくい総合的な見え方やブラウザ固有の崩れを確認するために使う。コード構造や geometry test で保証できるレイアウト不変条件の主たる保証を screenshot の比較や目視調整だけに置かない。

## 3. Small / Medium / Large

Test Size と Test Scope は別軸として扱う。Scope はテストが対象とする範囲を表し、E2E は Scope の一つである。Small / Medium / Large は、Google の考え方に沿ってテスト実行時に必要な resource と外部依存で分類する。

分類は対象モジュール名ではなく、必要とする実行環境と外部依存で判断する。

### Small Test

- 単一プロセス内で完結する。
- 実ネットワークを使用しない。
- 実 DB を使用しない。
- filesystem を使用しない。
- 外部 I/O は fake、mock、MSW 等で置き換える。

主な対象:

- Domain の状態遷移、権限、時給選択、給与集計
- 各業務モジュールの Application における認証・認可、service orchestration、error semantics
- Server Component / Server Action に接続する server helper と action 境界
- staff/admin の Component Test

Small Test は React の表示ロジック、利用者操作、状態変化を自動で検証する。Storybook の表示確認とは目的が異なり、操作後の結果や状態遷移の回帰を継続して検出する。

### Storybook

Storybook は認証・session・DB なしで UI を単独表示し、通常・空状態・代表的な状態を素早く目視確認する。mobile viewport も確認でき、UI 開発と review の反復を短縮する。Storybook は自動テストの代替ではなく、表示ロジック・利用者操作・状態変化は Small Test で保証する。

### Medium Test

- 単一マシン内で完結する。
- localhost、実 DB、filesystem、複数プロセス、実ブラウザなどを利用できる。
- 外部サービスへ依存しない。

実 PostgreSQL、Testcontainers、localhost の実サーバーなど、単一マシン内のプロセス外依存を利用するテストを含む。

主に DB query、transaction、constraint、migration の性質を保証する。

共有 Preview DB をテスト先に使用しない。Production 環境を導入した場合も、その DB を自動テストの検証先として使用しない。

### Large Test

外部ネットワークや外部システムへの依存を許容するサイズ。共有 remote DB、実 LINE Platform、実 Vercel Preview、その他の外部サービスなどへの依存を含むテストを対象とする。

現在、本システムには Google の resource-based classification における Large Test は存在しない。

Playwright による staff/admin の主要ユーザーフローと、axe によるアクセシビリティ検査は、broad-scoped E2E であるが Medium-sized E2E とする。現在の Playwright suite は Chromium、localhost 上の Next.js、同一マシン上の実 PostgreSQL を使用し、実 LINE Platform、実 Vercel Preview、共有 remote DB、その他の外部サービスへ依存しない。実 PostgreSQL 18 が必要で、通常は Testcontainers を使用する。`TIME_CARD_TEST_POSTGRES_MAINTENANCE_URL` を明示した場合は、テスト専用 localhost PostgreSQL 18 も利用できる。E2E は実際の Next.js runtime、認証・session、DB 更新、Server Action、画面遷移、axe を検証する。viewport ごとの横はみ出しや bounding box によるレイアウト不変条件も、実ブラウザで保証する必要がある場合はここで検証する。Storybook があっても、これらの保証を弱める形で E2E を削除しない。明確に視覚確認だけを重複しているケースは整理できるが、判断がつかない場合は維持する。

axe による検査は、自動検出可能なアクセシビリティ違反の回帰防止を目的とし、手動評価やすべてのアクセシビリティ問題の検出を代替するものではない。

## 4. 保証責務

| 対象                                                           | 主な保証先 |
| -------------------------------------------------------------- | ---------- |
| 純粋な業務ルール・状態遷移                                     | Small      |
| Application の認証認可・service orchestration                  | Small      |
| Server Component / Server Action の server 境界                | Small      |
| React の利用者操作・表示状態                                   | Small      |
| UI の単独表示・通常/空/代表状態の素早い目視確認                | Storybook  |
| PostgreSQL 固有の query / transaction / constraint / migration | Medium     |
| staff/admin の主要ユーザーフロー                               | Medium     |
| ブラウザ上のアクセシビリティ                                   | Medium     |

個別の境界値、入力、期待結果は対応するテストコードで定義する。

## 5. 命名規則

テストファイルは、対応する Size の suffix を使用する。

- `*.small.test.*`
- `*.medium.test.*`
- `*.large.test.*`

staff/admin の Vitest による Component Test は Small Test として `*.small.test.ts` または `*.small.test.tsx` を使用する。

Playwright による現在の E2E は Medium Test として `apps/e2e/tests/*.medium.test.ts` に配置する。E2E かどうかは `apps/e2e` という Scope と配置で表し、`.spec` は Playwright の識別子として扱わない。

## 6. 実行方法

リポジトリルートから実行する。

Storybook は `pnpm storybook` で起動する。認証や実 DB を必要とせず、表示する story を選んで各状態や viewport を確認できる。Storybook の static build は `pnpm build:storybook` で実行でき、`pnpm quality` と runtime 変更時の `pnpm quality:affected` に含まれる。`quality:affected` では static-only の変更時だけ省略する。

```sh
pnpm test:small
pnpm test:medium
pnpm test:e2e
```

`pnpm test:medium` は全 Medium Test を実行し、現在の Playwright E2E と axe による検査も含む。`pnpm test:e2e` は Size を問わず E2E Scope 全体を実行する入口とする。

Playwright E2E の正式な Medium Test は `apps/e2e` の `test:medium` で、Turbo による production build と `next start` を使用する。ローカル開発中には、同じ Medium E2E を build なしで Webpack を指定した `next dev` に対して実行する `pnpm --filter e2e test:medium:dev` を利用できる。この開発用 runner は Next.js の逐次コンパイルを安定させるため 1 worker で実行する。Medium Test 全件を実行する場合は `pnpm test:medium` を使用する。変更影響範囲に限定した Medium Test の実行には `test:medium:affected` があるが、通常の品質確認では「7. 品質ゲート」に記載する `pnpm quality` または `pnpm quality:affected` を使用する。`develop` の push CI では、`TURBO_SCM_BASE` に push 直前の SHA、`TURBO_SCM_HEAD` に今回の検証対象 SHA を指定する。

Playwright E2E の初回実行時など、Chromium が未導入の場合は次を実行する。

```sh
pnpm --filter e2e install:chromium
```

個別 package の実行方法やその他の具体的な script は各 `package.json` とテスト設定を Source of Truth とする。

Medium Test には実 PostgreSQL 18 が必要である。通常は Testcontainers と Docker 等のコンテナランタイムを利用するが、`TIME_CARD_TEST_POSTGRES_MAINTENANCE_URL` にテスト専用 localhost PostgreSQL 18 の maintenance database を明示して利用できる。リポジトリルートでは package 間の競合を避けるため `test:medium` を `concurrency=1` で集約するが、各 runner 内部の並列性はその runner の設定に従う。

## 7. 品質ゲート

リポジトリ全体を検証する標準の品質ゲートは次で実行する。

```sh
pnpm quality
```

`pnpm quality` は比較元を必要とせず、静的チェック、typecheck、Small Test、アプリケーション build、Storybook static build、Medium Test を含む全件の標準品質確認を行う。アプリケーション build と Storybook static build は別々の必須 stage として結果に表示する。Storybook static build は認証・session・実 DB・外部サービスを必要としない。現在の Medium Test には Playwright E2E と axe による検査も含まれる。

`pnpm quality:affected` は Git の比較範囲と workspace の依存関係から、安全に限定できる場合だけ影響範囲を絞る。比較範囲や影響を確定できない場合、未分類または global-impact の変更を含む場合、関連 E2E を限定できない場合は必要な全件確認へフォールバックし、判定失敗を「テスト 0 件の成功」として扱わない。

通常の feature branch では typecheck と Small Test を基本とし、変更の主要な保証が Medium Test にある場合は対応する Medium Test も実行する。`develop` の pre-push / push CI は `quality:affected`、`develop` 向け pull request と `main` は `quality` を使用する。Preview / Production deployment は対象 branch の Quality が成功した検証済み revision だけを候補とする。

品質ゲートの実行順、fallback、cache、branch ごとの CI 条件などの実装詳細は、ルート `package.json`、`scripts/run-quality.mjs`、`scripts/quality-affected.mjs`、`turbo.json`、`lefthook.yml`、`.github/workflows/quality.yml` を Source of Truth とする。

テスト追加時は coverage の増加自体を目的にせず、どの要求・リスクをどの境界で保証するかを優先する。

## 8. Property-based Test

`packages/payroll` では必要に応じて fast-check を利用する。

失敗時に出力される `seed` と `path` で反例を再現し、原因修正後も恒久的に守る価値がある反例は具体例ベースの回帰テストとして残す。

## 9. テストデータ・機密情報

- Production 環境を導入した場合、その実データを自動テストへ使用しない。
- 実ユーザー ID、アクセストークン、接続文字列、デプロイ ID 等をテストデータへ記載しない。
- fixture / fake は必要最小限の架空データとする。
- 実 PostgreSQL を使うテストはテスト専用の一時 DB を利用する。

## 10. テスト環境設定

通常の自動テストは、開発者がローカル開発のために保持する `.env`、`.env.local`、`.env.*.local` 等のアプリケーション設定を暗黙の入力として使用しない。

テストに必要なアプリケーション設定は、テストコードまたはリポジトリで管理するテスト専用設定から再現可能な形で与える。同名の環境変数が実行元プロセスに存在する場合も、それによって通常の自動テストの前提が意図せず変更されないようにする。

環境変数の読み込み・検証そのものを対象とするテストでは、正常値、不足値、不正値をテストケース自身が明示的に構築する。開発・本番実行時はテスト用設定へ置き換えず、実際の環境設定を使用し、不足または不正な必須設定を従来どおり拒否する。

OS、PATH、Docker、実ブラウザ等、テストレベル上必要な実行基盤はアプリケーション設定とは分けて扱う。Medium Test のコンテナランタイムや Playwright E2E のブラウザなど、外部実行環境が必要な場合は、その依存を実行方法から確認できる状態にする。
