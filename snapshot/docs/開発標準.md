# 開発標準

人と AI エージェントが共通して適用する変更単位、計画、検証、テスト、順序依存の挙動、利用者向け成果物の品質確認に関する標準を定める。

具体的な品質確認 command とその実行条件は `CONTRIBUTING.md`、`package.json`、関連 script、hook、CI 設定を Source of Truth とする。

## JavaScript module format

root package と `pnpm-workspace.yaml` が所有する全 workspace は ESM (`"type": "module"`) を標準とする。自作の CommonJS source (`.cjs` / `.cts`) は追加しない。tool の仕様などで例外が必要な場合は対象 file と理由を品質検査の明示的な allowlist に記録し、最小範囲に限定する。依存 package、生成物、build output は自作 source として扱わない。

## 変更単位

変更は 1 つの関心事を単位とする。独立した関心事を 1 つの変更へ混在させない。同じ関心事に属する実装、test、文書更新は、層やファイルが異なることだけを理由に分割しない。

Task は目的を独立して説明でき、実装・検証・review まで完了可能な変更単位とする。大きな変更を複数段階に分ける場合、各段階は目的、完了状態、検証を独立して説明できるものとする。前の段階の完了状態が後の段階の前提になる場合に限り、段階間に順序を設ける。

## 計画

計画から、目的、変更後に成立しているべき状態、変更範囲、正しさを確認する validation / review、同じ変更で更新する文書とその責務を判断できるようにする。前提となる Task や state がある場合はその条件も明記する。

## 実装品質の評価

実装品質はコード行数の増減を主な根拠に判断しない。コード行数、差分量、重複数等の定量値は、複雑さの移動や変更規模を把握するための補助情報として扱う。

品質判断では、コードを読んだときに意図と処理の流れを局所的に理解できること、責務と境界が自然であること、変更時に確認・修正すべき箇所と影響範囲を追いやすいことを優先する。型、API、control flow、error contract、共通化は、それ自体の短さではなく、利用側を含めた理解しやすさと保守しやすさで評価する。

明示的なコードが増えても、読みやすさ、保守性、安全性、責務の明確さが高まるなら、コード行数の増加だけを理由に低品質と評価しない。逆に、コード行数の削減や共通化によって局所理解、型の自然さ、変更追跡性が悪化する場合は、品質向上とはみなさない。

## 検証の進め方

同一条件の validation を偶然の PASS まで繰り返さない。単純 retry は再現性確認のため原則 1 回までとし、その後は failing test、runtime log、並列度、共有 resource 等の小さな診断で仮説を確認する。

skip、根拠のない assertion 緩和、根拠のない待機時間の増加、検証対象の runtime contract を変える workaround だけで green にしない。

## テスト

テストは、要求・業務ルール・利用者や呼び出し側から観測可能な振る舞い・境界の契約を継続的に検証する実行可能な仕様例として扱う。要求の背景、設計意図、運用判断や個別テストケースの詳細を文書とテストコードで重複管理せず、要求・設計・運用は各文書、具体的な入力・期待結果はテストコードを Source of Truth とする。

標準的なテスト・品質確認 command は `CONTRIBUTING.md`、runner、worker、build、affected 判定、cache 等の実装詳細は `package.json`、test config、Turbo / CI 設定、関連 script を Source of Truth とする。

### 基本方針

- 不具合は、対象の性質を直接保証できる範囲で最も内側の低コストなテストで検出する。
- 実 DB、filesystem、実ブラウザ等が必要な性質だけを外側のテストへ持ち出す。
- 一つの仕様には主な保証先を定め、同じケースを複数のテストレベルで機械的に重複検証しない。
- coverage の増加や正常系の網羅自体を目的にせず、変更による主要リスク、境界値、不正な状態遷移、認証・認可、競合、時刻・金額等の重要なケースを優先する。
- テストコード自体も保守対象とし、外部仕様を変えないリファクタリングで多数のテスト修正が必要になる場合は、実装詳細への結合を見直す。
- 通常の自動テストで使用するアプリケーション設定は、テストコードまたは repository で管理するテスト専用設定から決定的に与え、開発者ローカルの設定へ暗黙依存しない。
- Docker、実ブラウザ等の外部実行環境への依存は、必要なテスト分類と実行設定から確認できる状態にする。

### Small / Medium / Large

自動テストは、対象モジュールや runner 名ではなく、実行時に必要な resource と外部依存で Small / Medium / Large に分類する。

- **Small**: 単一プロセス内で完結し、実ネットワーク、実 DB、filesystem を使用しない。外部 I/O は fake、mock、MSW 等で置き換える。
- **Medium**: 単一マシン内で完結し、localhost、実 DB、filesystem、複数プロセス、実ブラウザ等を利用できるが、外部サービスへ依存しない。
- **Large**: 外部ネットワークまたは外部システムへ依存する。共有 remote DB、実 LINE Platform、実 Vercel Preview 等への依存を含む。現時点では Large Test を標準の自動テストとして持たない。

Storybook を人が目視するだけの場合は自動テストの Size 分類に含めない。Story を実 Chromium で自動実行する Storybook Browser Test は Medium とする。Storybook、Vitest、Playwright 等の環境・runner 名自体を Test Size として扱わない。

主な保証先は次を基本とする。

| 対象                                                                                                   | 主な保証先               |
| ------------------------------------------------------------------------------------------------------ | ------------------------ |
| 純粋な業務ルール・状態遷移                                                                             | Small                    |
| Application の認証・認可、service orchestration                                                        | Small                    |
| Server Component / Server Action に接続する server 境界                                                | Small                    |
| React の利用者操作・表示状態                                                                           | Small                    |
| UI の単独表示・通常 / 空 / 代表状態の目視確認                                                          | Storybook                |
| 単画面 UI の responsive / overflow / geometry / Dialog / 状態別 accessibility                          | Storybook Browser Medium |
| PostgreSQL 固有の query / transaction / constraint / migration                                         | Medium                   |
| 認証・session・DB・Server Action・実ページ遷移・reload・browser history を含む主要な実アプリ統合フロー | Web Medium               |
| 実アプリ統合フローにおけるブラウザ上の accessibility                                                   | Web Medium               |

単画面 UI で完結する実ブラウザ保証を Storybook Browser Medium へ置くことを理由に、実アプリを横断する統合保証を削らない。一方、同じ要求を Storybook Browser Medium と Web Medium の双方で網羅的に重複させない。

### テスト設計

- テスト名は前提または条件と保証する振る舞いが分かる名前にし、Issue 番号や過去の変更経緯を残さない。
- 利用者や呼び出し側から観測できる結果を優先し、DOM 構造、CSS class、内部関数の呼び出し回数等は、それ自体が契約でない限り固定しない。
- 組み合わせが多い状態遷移や条件は、必要に応じて状態遷移表や決定表で整理する。
- 広い入力範囲に対する不変条件は、具体例の列挙より Property-based Test が適する場合に利用する。失敗時に得られた反例のうち恒久的に守る価値があるものは、必要に応じて具体例ベースの回帰テストとして残す。
- 不具合修正では、可能な限り修正前に失敗する回帰テストで再現し、修正後も保証として残す。
- 一つのテストは主に一つの理由で失敗するように保つ。
- UI では操作可否、表示状態、accessibility、画面幅による操作不能や overflow 等、利用者に影響する振る舞いを保証する。CSS class、色値、絶対座標、ピクセル値は、明示的なデザイン契約でない限り固定しない。
- キーボード操作が独立した要件または主要リスクでない場合、標準 HTML や UI ライブラリの標準挙動を専用テストで重複保証しない。
- 列境界、配置、表示領域の幅等が明示的なデザイン契約の場合は、実ブラウザで要素間の相対位置、共通幅、余白等の不変条件を数値検証してよい。sub-pixel rounding を超えて不要に広い許容差を設けない。
- screenshot と目視確認は総合的な見え方やブラウザ固有の崩れの確認に使い、コード構造や geometry test で保証できる不変条件の主保証にはしない。
- axe 等の自動検査は検出可能な accessibility 違反の回帰防止に利用できるが、手動評価やすべての accessibility 問題の検出を代替するものではない。

### 命名

自動テストファイルは Size に対応する suffix を使用する。

- `*.small.test.*`
- `*.medium.test.*`
- `*.large.test.*`

Component Test でも実ブラウザを使う場合は Medium とする。実アプリ統合フローの browser test は Web workspace の対象 route / feature に配置し、Size に従って命名する。Storybook Browser Medium の対象と実行方法は Storybook / Vitest の設定を Source of Truth とする。

### テストデータ・環境

- Production の実データを自動テストへ使用しない。
- 実ユーザー ID、access token、接続文字列、deployment ID 等をテストデータへ記載しない。
- fixture / fake は必要最小限の架空データとする。
- 実 PostgreSQL を使うテストはテスト専用の一時 DB を利用する。
- 通常の自動テストは、開発者の `.env`、`.env.local`、`.env.*.local` 等をアプリケーション設定の暗黙の入力にしない。
- 環境変数の読み込み・検証自体を対象とするテストでは、正常値、不足値、不正値をテストケース自身が明示的に構築する。
- OS、PATH、Docker、実ブラウザ等の実行基盤はアプリケーション設定と分けて扱う。

## 順序・遷移を伴う振る舞い

正しさがイベント、状態遷移、非同期処理、副作用、説明と操作などの順序や timing に依存する変更では、その順序自体を検証する。最終状態だけを根拠にしない。

要求上意味のある before / after、状態遷移、実行順序は tests、実挙動、frame、log 等の適切な証拠で確認する。timing 自体が要件でない場合、固定 sleep の長さだけを同期条件にしない。

## 利用者向け成果物

画面、文書、画像、動画など利用者が直接見る成果物では、技術的な正しさと利用者品質を別の review 軸として扱う。実際の render、画面、frame、出力文書を根拠に、読みやすさ、分かりやすさ、文言、操作・説明の順序、不要な表示、画面状態との整合を判断する。tests、build、metadata、生成 command の成功だけでは利用者品質を保証しない。

ユーザーに見える画面のブラウザ確認では、変更された実際の route / page を対象とする。一時 page / component は代替証拠にならない。browser review 用の一時ファイルや生成物は tracked file に残さない。
