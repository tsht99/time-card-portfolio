## 1. 文書の役割

本書は、本システムのローカル開発環境構築、外部サービス設定、DB migration、Vercel へのデプロイに必要な手順をまとめる。

システム構成自体は [設計書](./設計書.md)、テストの設計原則・分類・保証責務は [開発標準](./開発標準.md) の「テスト」を参照する。本書には本番バックアップ・復旧に固有の運用条件も含める。

## 2. 前提環境

必要な主なツール・サービス:

- Git
- Node.js
- pnpm
- Docker 等のコンテナランタイム（Medium Test 用）
- AWS CLI（Production DB backup の手動確認・restore 用）
- Vercel
- Neon PostgreSQL
- Cloudflare R2
- LINE Developers / LINE Login / LIFF
- 必要に応じて Sentry

ローカル開発で使用する Node.js の exact version は `mise.toml` を Source of Truth とする。pnpm は従来どおりルート `package.json` の `packageManager` を Source of Truth とする。Vercel の Node.js は `package.json` の `engines.node` で 24.x を指定し、minor / patch version は Vercel 側で更新される。

`apps/web` は staff、`/admin`、Server Components、Server Actions を提供する Next.js アプリとして単一の Vercel deploy 単位で運用する。`apps/help` は利用者向けガイドを提供する独立した Next.js アプリであり、Vercel では別 project として repository root directory を `apps/help` に設定する。両アプリの runtime、deployment、domain は独立している。

## 3. ローカル環境構築

```sh
git clone <REPOSITORY_URL>
cd TimeCard
pnpm install --frozen-lockfile
```

通常の Web 開発サーバー:

```sh
pnpm dev:web
```

利用者ガイドの開発サーバー:

```sh
pnpm dev:help
```

実 LINE / LIFF 認証を利用するローカル開発では `pnpm dev:web:liff` を使用する。詳細は「staff で実 LINE 認証を使うローカル開発」を参照する。

必要な環境変数名と設定有無は、`apps/web/.env.example`、root `.env.local.example`、各 server package の env 定義を Source of Truth とする。`dev:web:liff`、`db:migrate`、Drizzle schema / migration generation の Local 設定は root `.env.local` を唯一の入力とする。これらのコマンドは同ファイルの DB 値で inherited environment を上書きし、Local 条件や PostgreSQL URL が不足・不正なら DB 操作前に停止する。実値や secret はコミットしない。

各 workspace は、環境変数を実際に利用するフェーズで必要な値と形式を検証する。`NEXT_PUBLIC_*` のように build artifact へ埋め込まれる公開設定や、Sentry の source map upload のように build 処理自体が参照する設定は build-time configuration として build 時に利用・検証する。一方、`DATABASE_URL` や `LINE_CHANNEL_ID` のように build artifact へ埋め込まない server runtime 設定は Web build の必須入力にせず、実際にその設定を必要とする runtime 処理または明示的な runtime configuration validation で不足・形式不正を検出する。

build-time configuration と runtime configuration は一律に扱わない。runtime で必須の設定を optional 扱いにはせず、必要な runtime 境界で明確に失敗させる。

staff / admin 画面の「利用者ガイド」は `NEXT_PUBLIC_HELP_URL` を build-time configuration として使用する。有効な HTTP(S) の Help deployment URL を設定し、未設定・空・不正な値では Web build を失敗させる。ローカルでは root `.env.local` または `apps/web/.env.local` に設定し、Git 管理対象の例ファイルを参照する。Preview と Production では同じ変数名を使い、それぞれ対応する Help deployment URL を各 Vercel environment に設定する。URL の形式や固定 domain は前提にしない。

`pnpm quality` の build 検証と Web Medium Test は repository-managed の `https://help.example.test` を使う。これはテスト環境専用の値であり、Vercel 各環境の設定には使用しない。

標準品質確認:

```sh
pnpm quality
```

テスト分類は [開発標準](./開発標準.md) の「テスト」、標準的な実行コマンドは [CONTRIBUTING.md](../CONTRIBUTING.md) の Validation を参照する。

## 4. PostgreSQL / Neon

Local、develop / Preview、Production は接続先を分離する。共有 Preview DB や Production DB をローカルテストの検証先として使用しない。

DB 接続に必要な環境変数名は `packages/db/.env.example` と DB 実装を Source of Truth とする。Local の `DATABASE_URL` と `DATABASE_ENVIRONMENT=local` は root `.env.local.example` に対応する root `.env.local` へ設定する。`packages/db/.env.local` は読み込まない。Preview / Production の接続値は Vercel environment または明示的な maintenance operation の secret として管理する。接続文字列の実値は文書やソースへ記載しない。

Preview / Production で migration または Attendance Current State Projection rebuild を行う maintenance operation は、通常 runtime の `DATABASE_URL` とは分離し、`DATABASE_URL_UNPOOLED` の direct connection を使用する。`DATABASE_URL_UNPOOLED` が未設定の場合に `DATABASE_URL` へ fallback しない。

Preview / Production の maintenance operation では、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に期待する接続先 identity を設定する。これらは接続先を照合するための host / database 名であり DB credential ではない。接続文字列の host / database が期待値と一致しない場合、Neon の pooled endpoint が指定された場合、または接続後の `current_database()` が一致しない場合は、advisory lock や書き込みを開始せず停止する。接続先を推測して続行せず、設定を確認・修正してから再実行する。

remote PostgreSQL へ接続する場合は TLS 証明書検証を有効にし、`sslmode=verify-full` を利用する。localhost や Testcontainers など TLS を使用しないローカル接続では、この指定を前提としない。

DB schema と migration の Source of Truth は `packages/db` とする。

ローカル migration:

```sh
pnpm db:migrate
```

ローカル migration と Drizzle schema / migration generation は root `.env.local` を読み、そこにある Local 設定だけで接続先を決定する。shell から継承した DB 値や `packages/db/.env.local` は使わない。Local 条件を満たさない設定では DB へ接続せず停止する。共有 Preview DB や Production DB をローカル操作の対象にしない。適用済み migration の内容を書き換えて履歴を変更せず、schema 変更には新しい migration を追加する。

### Production DB backup

Production DB の論理バックアップを Cloudflare R2 へ保存するため、GitHub Actions の `.github/workflows/backup-production-db-scheduler.yml` と `.github/workflows/backup-production-db.yml` に必要な環境を構築する。

backup の実行頻度、dump / checksum 生成、object key 等の実装詳細は [scheduler workflow](../.github/workflows/backup-production-db-scheduler.yml) と [backup workflow](../.github/workflows/backup-production-db.yml) を Source of Truth とする。本書では構築に必要な設定、保持方針、復旧判断・検証時の安全条件を扱う。

#### Cloudflare R2

1. Production DB backup 専用の R2 bucket を作成し、公開アクセスを有効にしない。
2. Production backup は **30 日保持**を運用方針とする。bucket の Object Lifecycle Rule で prefix `production/` の dump と対応する `.sha256` をともに 30 日後に expire する。実際の設定と object の存在を確認し、保持期間を超える復旧を前提にしない。
3. workflow 専用 R2 API token を作成し、権限を Object Read & Write、対象をこの backup bucket のみに限定する。bucket 作成や Lifecycle Rule 変更を行える管理権限は付与しない。
4. token 作成時に取得した Access Key ID / Secret Access Key と Cloudflare Account ID、bucket 名を GitHub 側へ登録する。実値は repository や文書へ記録しない。

#### PostgreSQL backup role

Production DB の通常 application credential を GitHub Actions へ複製せず、backup 専用 login role `timecard_backup` を使用する。

Production database owner で次を実行する。password は十分に強いランダム値を生成し、実値を shell history、Issue、文書へ残さない。

```sql
CREATE ROLE timecard_backup LOGIN PASSWORD '<generated-strong-password>';
GRANT CONNECT ON DATABASE neondb TO timecard_backup;
GRANT pg_read_all_data TO timecard_backup;
ALTER ROLE timecard_backup SET default_transaction_read_only = on;
```

`timecard_backup` に SUPERUSER、CREATEDB、CREATEROLE、REPLICATION、BYPASSRLS や個別の書き込み権限を追加しない。現行 schema は RLS を使用していない。将来 RLS を導入する場合、`pg_read_all_data` は RLS を bypass しないため、backup role から全対象行を dump できることを改めて検証する。

Neon Console で role に `timecard_backup`、database に `neondb`、direct connection を選び、TLS 証明書検証を有効にした `sslmode=verify-full` の接続文字列を取得する。この実値を GitHub Environment `production` の Secret `PRODUCTION_DATABASE_BACKUP_URL` として保存する。

#### GitHub Actions 設定

GitHub Environment `production` の Secrets:

- `PRODUCTION_DATABASE_BACKUP_URL`: `timecard_backup` で Production `neondb` へ接続する direct connection string
- `R2_BACKUP_SECRET_ACCESS_KEY`: backup bucket のみに scope した R2 Secret Access Key

GitHub Environment `production` の Variables:

- `R2_BACKUP_ACCESS_KEY_ID`: 対応する R2 Access Key ID
- `R2_BACKUP_BUCKET`: Production DB backup 用 bucket 名

Repository Variables:

- `R2_BACKUP_ACCOUNT_ID`: Cloudflare Account ID

Production 固有の 2 つの Secret（`PRODUCTION_DATABASE_BACKUP_URL`、`R2_BACKUP_SECRET_ACCESS_KEY`）と 2 つの Variable（`R2_BACKUP_ACCESS_KEY_ID`、`R2_BACKUP_BUCKET`）は、Repository scope に重複登録しない。

初期設定後は GitHub Actions の `Production DB Backup` workflow で ref に `main` を選んで手動実行し、成功した run が R2 に `.dump` と対応する `.dump.sha256` を作成することを確認する。default branch の選択状態をそのまま信用せず、実行前に `main` であることを確認する。object が存在するだけでは restore 可能性の確認にはならないため、**本番運用開始前**に以下の「Production DB の復旧・検証」に従って隔離環境への初回 restore を手動で検証する。

### Production DB の復旧・検証

Production DB は Neon の point-in-time recovery（短期履歴）と Cloudflare R2 の論理バックアップ（独立コピー）を使い分ける。障害時は、Neon の実際の history retention、R2 の保持設定、利用可能な復旧地点を現在のサービス設定・保存済み object から確認する。

- 原本データが正常で Current State Projection のみが不整合な場合は、DB restore ではなく既存の Projection rebuild を使う。アプリケーションの問題については、現在の DB schema と Event format に対する旧 revision の互換性を確認し、互換性が不明な rollback を強行しない。
- データが正常だった最後の時点と、失われ得る更新の範囲を特定する。必要な復旧地点が Neon の短期履歴から利用できる場合は、その履歴を第一候補として検証する。履歴の対象外である場合や独立コピーが必要な場合は R2 backup を検討する。
- R2 から復元する場合は、対象時刻、dump と対応する checksum、dump の読み取り可能性を確認する。download、checksum、復元に失敗した backup を復旧元として採用しない。
- backup の実行成功や object の存在のみでは復元可能とみなさない。Production と共有 Preview / Local のどれでもない、隔離された復元専用 DB で実際に restore し、主要データ、migration history、対象 application revision の schema / Event format 互換性を検証する。**検証目的で Production DB に restore しない。**
- backup pipeline、PostgreSQL major version、R2 credential、復元方式を変更した場合は、Production を変更せず、隔離環境への restore 検証を再実施する。
- 本番運用開始後は、最後に復元検証が成功した日から **4 週間以内** に、R2 の実バックアップを隔離環境へ手動で restore し、同じ検証を行う。初回・変更時の検証成功も起算点に含める。実施漏れを防ぐため、成功から 3 週間を目安に次の検証を予定する。
- 検証では実施日・対象バックアップ・結果を、秘密情報や個人情報を含めずに記録する。失敗時は成功扱いにせず、原因を調査して再検証する。
- 本番の復旧先を切り替える前に、復旧地点以降のデータ損失と、新規書き込みが旧 Production と新しい復旧先に分岐するリスクを評価し、必要に応じて書き込みを停止する。復元検証と互換性確認が完了するまでは Production 接続先を変更しない。
- 復旧後は実際の公開 deployment と DB の対応、staff / admin の主要機能を確認する。検証用リソースの削除対象に Production・共有 Preview・通常の Local データを含めない。

### Production 初期管理者の設定

Production の初期 admin は、専用 CLI や恒久的な role 変更 UI / API ではなく、Production DB に対するシステム運用者の明示的な手動操作で設定する。既に active admin がいる状態での admin 追加・昇格・降格には、この初期設定手順を使わない。

#### 事前確認

1. 初期 admin にする本人が Production LINE / LIFF から一度ログインし、`users` row が作成済みであることを確認する。
2. 対象は本人確認済みの LINE identity に対応する `line_user_id` で特定する。display name だけを根拠に対象を決めない。
3. Neon / Vercel の現在設定から Production DB 接続先を確認し、接続後も host と database name を照合して Production DB であることを明示確認する。
4. 対象 user が `staff / pending` であり、`admin / active` の user がまだ存在しないことを確認する。どちらかが異なる場合は更新せず、状態を調査する。
5. DB 接続文字列や LINE user ID の実値を repository、Issue、共有ログへ記録しない。作業記録にも秘密値を含めない。

#### 条件付き更新

Production DB へ接続した `psql` セッションで `\echo :HOST / :DBNAME` を実行して接続先を再確認し、次のように対象状態を確認する。LINE user ID は `\prompt` でその場に入力し、SQL コマンド履歴や記録へ実値を残さない。

```sql
\prompt 'Verified LINE user ID: ' verified_line_user_id

BEGIN;
LOCK TABLE users IN EXCLUSIVE MODE;

SELECT role, status
FROM users
WHERE line_user_id = :'verified_line_user_id';

SELECT count(*) AS active_admin_count
FROM users
WHERE role = 'admin' AND status = 'active';
```

対象が一件の `staff / pending` であり、active admin が 0 件の場合に限り、同じトランザクション内で続けて実行する。

```sql
UPDATE users AS target
SET role = 'admin', status = 'active'
WHERE target.line_user_id = :'verified_line_user_id'
  AND target.role = 'staff'
  AND target.status = 'pending'
  AND NOT EXISTS (
    SELECT 1 FROM users AS existing_admin
    WHERE existing_admin.role = 'admin'
      AND existing_admin.status = 'active'
  )
RETURNING role, status;

SELECT role, status
FROM users
WHERE line_user_id = :'verified_line_user_id';
```

`RETURNING` が一行を返し、更新後の確認でも対象が `admin / active` の場合だけ `COMMIT` する。それ以外は `ROLLBACK` し、条件を調査する。事前条件を満たさない状態を無条件更新で上書きしない。

設定後は本人が Production LIFF に再ログインし、`/admin` と既存のユーザー管理機能を利用できることを確認する。確認に失敗した場合は追加の role / status 変更をせず、認証・認可、Production deployment、server log を調査する。

## 5. LINE Login / LIFF

staff と `/admin` は LINE Login / LIFF から認証情報を取得し、Server Action から `modules/users` の authentication application へ渡す。`apps/web` の Composition Root が LINE 検証 adapter と PostgreSQL adapter を組み立て、本システムのセッションを作成する。

内部業務処理は同じ Next.js アプリ内の Server Components / Server Actions から server application を直接利用するため、別 API origin、CORS 用の許可 origin、ブラウザ向け業務 API base URL は設定しない。具体的な設定項目は `apps/web/.env.example`、root `.env.local.example`、各 env 定義を Source of Truth とし、Vercel またはローカル `.env` へ設定する。

### staff で実 LINE 認証を使うローカル開発

staff を実際の LINE アカウントで認証しながらローカル確認する場合は、Production / 公開中の LIFF アプリとは別に、ローカル専用の LIFF アプリを使用する。LINE Login Channel は既存の開発用 Channel を利用できるが、ローカル用 LIFF アプリ自体は共有 Preview や公開中の LIFF アプリと分離し、Endpoint URL を `https://localhost:3000` に固定する。

ローカル確認では次の経路を使用する。

```text
ローカル専用 LIFF
  ↓
https://localhost:3000
  apps/web (Next.js HTTPS)
  ├─ staff
  ├─ /admin
  └─ Server Components / Server Actions
       ↓
Local / 開発専用 DB
```

内部業務処理のために別 API process、開発用 proxy、port 8787 は使用しない。ブラウザから汎用的な same-origin REST API を呼び出す構成にも戻さない。ローカル開発のために本番の認証方式や session cookie のルールを緩和しない。

#### 初回セットアップ

1. 開発用 LINE Login Channel にローカル専用 LIFF アプリを用意する。共有 Preview や Production / 公開中の LIFF アプリを流用しない。
2. LINE Developers でローカル専用 LIFF アプリの Endpoint URL を `https://localhost:3000` に設定する。ローカル専用アプリとしてこの値を固定し、日常の起動時には変更しない。
3. `mkcert` をインストールし、ローカル CA を初期化する。

   ```sh
   mkcert -install
   ```

4. リポジトリ root で localhost 用証明書を作成する。

   ```sh
   mkcert localhost
   ```

   `localhost.pem` と `localhost-key.pem` は Git 管理しない。

5. Production / 共有 Preview ではない Local または開発専用 DB を用意する。実運用データは使用しない。
6. root の `.env.local.example` を `.env.local` としてコピーし、ローカル用の値を設定する。

   ```sh
   cp .env.local.example .env.local
   ```

   主な設定は次のとおり。

   - `DATABASE_URL`: Local または開発専用 DB
   - `DATABASE_ENVIRONMENT=local`（runtime は node-postgres で接続する）
   - `LINE_CHANNEL_ID`: ローカル専用 LIFF アプリが属する開発用 LINE Login Channel
   - `NEXT_PUBLIC_LIFF_ID`: ローカル専用 LIFF アプリの LIFF ID

   内部業務処理は `apps/web` 内の Server Components / Server Actions から実行するため、ローカル用の業務 API base URL や別 API port は設定しない。

#### 日常の起動

初回セットアップ後は root で次を実行する。

```sh
pnpm dev:web:liff
```

launcher は root `.env.local` と localhost 証明書を検証し、Local DB migration の成功後に `apps/web` を `https://localhost:3000` で起動する。staff、`/admin`、Server Components / Server Actions はこの 1 つの Next.js process から提供される。root の mkcert 証明書を使って HTTPS で直接起動するため、日常の起動時に LINE Developers の Endpoint URL を変更する必要はない。

起動後は `https://liff.line.me/<NEXT_PUBLIC_LIFF_ID>` を開き、実際の LINE ログインを完了する。認証後に本システムの staff 画面が認証済み状態になり、勤怠データを取得できることを確認する。書き込みを含む確認が必要な場合は打刻も実施し、session cookie と Server Action の経路で正常に完了することを確認する。

実 LINE ログインは手動確認用であり、自動テストでは従来どおり fake / mock を使用する。

## 6. Vercel

`apps/web` は staff、`/admin`、Server Components、Server Actions を提供する単一の Vercel project として deploy する。`apps/help` は利用者向けガイドを提供する独立した Vercel project とし、repository root directory を `apps/help` に設定する。Web と Help は deployment、environment、domain を分離する。

Vercel project の build 設定は各 `vercel.json` と package scripts、GitHub Actions からの deployment 条件・順序・並行実行制御は `.github/workflows/`、Vercel Deployment API の呼び出しと source / project / deployment 検証は `scripts/deploy-*.mjs` を Source of Truth とする。本書では workflow の job 名、concurrency group、内部判定式、API payload、cache option 等を複製せず、環境構築と運用時に必要な条件だけを扱う。

`apps/help` は Vercel Git integration による自動 deployment を使用せず、Preview / Production とも GitHub Actions から deploy する。Repository Secret `VERCEL_TOKEN` と Repository Variable `VERCEL_ORG_ID` は Web / Help の両 project に共通で使用する。Repository Variables は Web 用 `VERCEL_PROJECT_ID` と Help 用 `VERCEL_HELP_PROJECT_ID` をそれぞれ設定し、project ID を混同しない。これらの GitHub 設定は Preview / Production deployment で使用し、application runtime secret を deployment 起動用設定へ複製しない。

Help の Preview / Production build では `HELP_SCREENSHOT_BASE` と `HELP_VIDEO_BASE` を各 Vercel environment に設定する。Preview は Preview Neon Storage、Production は Production Neon Storage の `time-card-help` bucket にある対応 prefix を参照する。repository や文書へ実 endpoint / credential を固定値として記載しない。ローカルの `pnpm dev:help` では生成済み screenshot を自動参照し、video base 未設定時は動画を表示しない。

Web の Preview / Production environment には、それぞれ対応する Help deployment を指す `NEXT_PUBLIC_HELP_URL` を設定する。

### develop Preview

`develop` push の Quality 成功後、Web Preview と Help Preview はそれぞれ独立した GitHub Actions job から自動 deployment する。両方とも対象 push の exact SHA を使用し、実行時にその SHA が現在の `develop` HEAD であることを確認する。古くなった run は skip する。Pull request から Preview deployment は行わない。Git 自動 deployment を無条件に有効化しない。

GitHub Actions の Preview deployment には Repository Secret `VERCEL_TOKEN` と Repository Variables `VERCEL_ORG_ID`、`VERCEL_PROJECT_ID`、`VERCEL_HELP_PROJECT_ID` が必要である。Web job は `VERCEL_PROJECT_ID`、Help job は `VERCEL_HELP_PROJECT_ID` を使用する。これらの設定は Production deployment と共有する。

deployment 後は Vercel deployment が READY であること、source SHA が対象 SHA と一致すること、target environment が Preview であることを確認する。さらに staff / admin の主要機能と Help への導線を確認する。Quality success だけを Preview 反映成功とはみなさない。

### Help Preview

Help Preview は Web Preview と独立した自動 deployment job で反映する。Vercel project は Web と分離し、root directory を `apps/help`、environment を Preview として設定する。deployment 後は Vercel deployment が READY であること、source SHA と target environment がそれぞれ対象 revision と Preview に一致することを確認する。Help の主要ページと screenshot / video media が表示されることも確認する。

### Production

Production deployment の反映元 branch は `main` とし、旧 `master` は Production migration / deployment の許可 branch として扱わない。Production は Quality を通過した現在の `main` revision だけを反映対象とし、Web と Help はそれぞれ GitHub Actions から Vercel へ deployment する。

Production deployment は検証済み exact revision を source として扱い、古い revision が後から現在の Production を巻き戻さないこと、対象 Vercel project / GitHub repository / `main` revision が一致することを repository-managed workflow / deployment script で保証する。具体的な判定方法、直列化、Vercel API option、READY 待機と metadata 検証は workflow / script を Source of Truth とする。

Production deployment 起動用の GitHub Actions 設定は `VERCEL_TOKEN`、`VERCEL_ORG_ID`、Web 用 `VERCEL_PROJECT_ID`、Help 用 `VERCEL_HELP_PROJECT_ID` を使用する。実値を文書・repository・workflow log に記載せず、application runtime や Production DB の secret と混同しない。

Quality と Production deployment は別の結果として扱う。Quality が成功していても deployment が失敗した場合は Production 反映成功とはみなさず、GitHub Actions と Vercel の deployment status から原因を切り分ける。

#### 現在の Production 反映先の確認

現在公開されている revision を確認するときは、GitHub の branch HEAD、CI / deployment の成功、Vercel deployment、public alias を別々の情報として確認し、同じ revision を指していることを照合する。

1. GitHub の `main` で対象となる exact SHA を確認する。
2. その SHA の Quality と Production deployment が成功していることを GitHub Actions で確認する。
3. Vercel 側で対象 deployment が READY であり、source が対象 repository の `main` と同じ exact SHA を指していることを確認する。
4. Production の public alias / domain がその deployment を指していることを確認する。deployment が READY であるだけでは、現在 public traffic がその deployment へ向いている証拠としない。
5. release 内容に応じて staff、`/admin`、実 LINE / LIFF 等の必要な smoke test を行う。

Vercel project、Production DB、LINE / LIFF、GitHub Actions / Vercel の設定を変更した場合は、変更した境界について現在値を再照合し、その後の Production release で必要な smoke test を再実施する。初回構築作業を通常の未完了タスクとして扱わない。

## 7. Web deployment と migration

`apps/web` の deployment では、必要な migration を Web build より前に適用する。migration はアプリケーション起動時や HTTP リクエスト処理中には実行せず、デプロイ処理上の明示的な step として扱う。

```text
環境ガード
  ↓
Maintenance DB 接続設定の検証
  ↓
接続先 DB identity の検証
  ↓
PostgreSQL advisory lock
  ↓
Drizzle migration
  ↓
Web build
```

`apps/web/vercel.json` の build command は migration gate の成功後に root の `build:web` を実行する。

現在の `apps/web/vercel.json` の Production build でも、`pnpm --filter @repo/db migrate:deploy` が成功した後に `pnpm -w build:web` が実行される契約を維持する。

DB migration command は Node.js の `development` export condition を有効にして `tsx` で実行する。これにより、migration から直接利用する workspace package は build 済み `dist` ではなく source export へ解決される。

この deployment pipeline では migration step が DB 接続設定を必要とするが、それは migration を実行するための deploy-time requirement であり、Web build artifact 自体の build-time requirement とは区別する。

Preview / Production の deploy migration では、maintenance 用 direct connection として `DATABASE_URL_UNPOOLED` を設定し、対象確認用に `DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` を設定する。通常 runtime が利用する `DATABASE_URL` は別の契約として維持し、maintenance connection の代替には使用しない。

`DATABASE_URL_UNPOOLED` は credential を含む secret として管理する。期待 host / database は接続先 identity として設定する。これらが欠落している、接続文字列が Neon pooled endpoint である、期待 host / database と一致しない、または接続後の database が一致しない場合、migration は advisory lock や schema 変更へ進む前に失敗する。

- deploy 時はリポジトリへコミット済みの migration だけを順番に適用し、schema 差分から migration を自動生成しない。
- 共有 Preview DB への deploy migration は `develop` からだけ実行し、feature / bugfix 等の作業ブランチから適用しない。
- 実行環境と migration 対象 DB の対応を安全に特定できない場合は、推測して続行せず停止する。
- Production DB への deploy migration は、Vercel Production context、`main` branch、`DATABASE_ENVIRONMENT=production` が一致する Production release だけで許可する。旧 `master`、Local、Preview、その他の branch / environment の組み合わせは fail closed で拒否する。
- migration の同時実行は advisory lock で抑止する。
- migration 失敗時は deployment を成立させない。
- migration 適用後に build が失敗しても DB を自動 rollback する前提にはしない。

migration 成功後に Web build または deployment が失敗すると、DB schema だけが先に進む場合がある。Application rollback は DB schema や保存済み Event を巻き戻さないため、旧 revision が現在の schema / Event format と互換であることを確認してから行う。互換性を確認できない場合は rollback を強行しない。

DB の復旧判断・検証時の安全条件は「Production DB の復旧・検証」を参照する。schema 変更では migration 適用後に旧版または新版の application が動く時間帯を考慮し、必要な backward compatibility と安全なデプロイ順序を設計する。

### Attendance Current State Projection の rebuild

Current State Projection は Event Store から再生成可能な派生データであり、Event Store を Source of Truth とする。Local では root の `.env.local` に Local 用設定を置いたうえで、明示的に次を実行する。

```sh
pnpm --filter @repo/attendance-projection-rebuild rebuild:local
```

Preview の rebuild は Vercel の build command へ組み込まない。Preview 初回導入では、Projection を維持でき、not-ready 状態を安全に扱える application version が active deployment へ切り替わったことを先に確認してから、post-deploy の明示的な maintenance operation として実行する。

実行前に、Preview DB の direct connection を `DATABASE_URL_UNPOOLED` として現在の shell に secret 設定し、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に対象 Preview DB の identity を設定する。あわせて `DATABASE_ENVIRONMENT=preview` と `ATTENDANCE_PROJECTION_REBUILD_CONFIRM=preview` を一時的に設定する。`DATABASE_URL_UNPOOLED` が無い場合に通常 runtime の `DATABASE_URL` へ fallback しない。その状態で次を実行する。

```sh
pnpm --filter @repo/attendance-projection-rebuild rebuild:preview
```

Production の rebuild も Vercel の build command へ組み込まない。Event Store が正常な Source of Truth として利用でき、Current State Projection の欠損・不整合または not-ready 状態を解消する必要がある場合だけ、明示的な maintenance operation として実行する。実行前に、現在 active な application が rebuild 中の not-ready 状態を安全に扱えることを確認する。

実行前に、Production DB の direct connection を `DATABASE_URL_UNPOOLED` として現在の shell に secret 設定し、`DATABASE_MAINTENANCE_EXPECTED_HOST` と `DATABASE_MAINTENANCE_EXPECTED_DATABASE` に対象 Production DB の identity を設定する。あわせて `DATABASE_ENVIRONMENT=production` と `ATTENDANCE_PROJECTION_REBUILD_CONFIRM=production` を一時的に設定する。`DATABASE_URL_UNPOOLED` が無い場合に通常 runtime の `DATABASE_URL` へ fallback しない。その状態で次を実行する。

```sh
pnpm --filter @repo/attendance-projection-rebuild rebuild:production
```

Production rebuild は Vercel の build / runtime 内では実行せず、Vercel environment と判定されない運用者の shell から明示的に実行する。Projection rebuild は Event Store から派生データを再生成する操作であり、原本データが破損・欠損している場合の DB restore の代替には使用しない。

Preview / Production rebuild は direct maintenance connection、期待 host / database、対象 environment、確認値をすべて照合できた場合だけ開始する。接続情報の実値は文書、Issue、command example、ログへ記載しない。復旧判断と安全条件は「Production DB の復旧・検証」を参照する。

## 8. Sentry / ログ

必要な環境では Sentry を有効化する。DSN、auth token、組織・プロジェクト設定等の実値は secret として管理する。

Vercel の deployment / runtime log と Sentry を用途に応じて確認する。アプリケーション独自の request log を稼働確認のためだけに維持しない。

## 9. デプロイ前後の確認

### デプロイ前

- 対象 branch / commit が正しい。
- 必要な環境変数が対象環境に設定されている。
- schema 変更がある場合、対応 migration が存在する。
- `pnpm quality` が成功している。
- 必要な場合 Large Test を実施している。
- Production の場合、release 対象が `main` の Quality 成功済み revision であることを確認する。
- Production の場合、Production DB / runtime secret / Vercel project 等の対象環境設定が揃っていることを確認する。
- Production deployment を手動で別 SHA に差し替えず、GitHub Actions の exact revision 経路を使う。

### デプロイ後

- 通常の staff 入口と `/admin` で認証と主要画面の初期表示を確認できる。
- 変更内容に対応する主要操作が成立する。
- 監視に新しい unexpected error がない。
- Production の場合、GitHub Actions の Production deployment が成功し、Vercel deployment が READY であることを確認する。
- Production の場合、Vercel deployment の source が `main` の Quality 済み revision と一致することを確認する。
- 各 release では現在の public alias が意図した deployment / SHA を指していることを確認し、変更内容に応じた smoke test を実施する。LINE / LIFF、DB、Vercel 等の Production 設定を変更した場合は、その境界も再確認する。
